# Changelog

This is the changelog of the software. The APC standard (the contract an app and an agent share) is versioned apart, with its own [changelog](packages/protocol/CHANGELOG.md). Every PR that changes behavior adds an entry under `## Unreleased`; see `AGENTS.md`.

## Unreleased

Everything that merged after `v0.2.0` (PRs #16 to #109) and has not been tagged yet. APC v2 (the dock, Signals, the extension and the desktop apps) was built in this stretch; v1 at apc.tineira.com keeps working as in 0.2.0.

### APC 0.7.1, the first CI publish, and an extension that says it is out of date (2026-11-04, TIN-613, TIN-612)

- **The four `@tineira/apc-*` packages and `APC_STANDARD_VERSION` are 0.7.1, with no change to the contract.** The doc comments name the published packages, not the old `@apc/*` ones; a tag `apc-v0.7.1` on `main` is the first publish through `publish.yml` and npm trusted publishing. (`packages/*/package.json`, `packages/protocol/src/version.ts`, `packages/protocol/src/core.ts`, `packages/protocol/src/manifest.ts`, `packages/protocol/CHANGELOG.md`)
- **`scripts/publish-local.mjs` installs with the frozen lockfile before it builds, and removes its `apc-publish-*` temporary folder** after a dry run, a publish or a failure (and on Ctrl+C), so stale workspace links from before a rename cannot break it and no tarballs are left behind. (`scripts/publish-local.mjs`, `scripts/lib/packages.mjs`, `scripts/lib/temp-folder.mjs`)
- **Every build of the browser extension has its own version, `0.2.<n>`, and the dock says when yours is out of date.** n counts the commits up to the extension's last change, so it only grows on `main`; the popup shows it with the commit, and the dock-presence script tells the page (`data-apc-extension-version`). The dock bakes in the same version at build time and is redeployed when the extension changes; `/dock` shows "Your APC extension is out of date" with a link to the update steps on `/extension`, which now say that Reload alone does not update it. A build from before this one reports no version and gets no notice; `/extension` says to download the latest zip if it stops working. The builds need the full git history, so CI checks it out. (`scripts/lib/extension-version.mjs`, `apps/extension/build.mjs`, `apps/extension/src/presence.ts`, `apps/extension/src/dock-presence.ts`, `apps/extension/src/popup.ts`, `apps/dock/vite.config.ts`, `apps/dock/src/web/extension.tsx`, `apps/dock/src/web/downloads.tsx`, `.github/workflows/ci.yml`, `.github/workflows/extension.yml`, `.github/workflows/publish.yml`)
- **A pull that changes the extension rebuilds `apps/extension/dist`, the folder loaded unpacked.** `pnpm install` points `core.hooksPath` at `.githooks` (only inside a git work tree, never failing); after a pull, merge, rebase or branch checkout that touches the extension's inputs, the hooks run `node build.mjs` (after `pnpm install --frozen-lockfile` when the lockfile changed) and print "APC extension rebuilt into apps/extension/dist: reload it on chrome://extensions"; a failed build only warns. Off: `git config --unset core.hooksPath`. (`.githooks`, `scripts/extension-changed.mjs`, `scripts/git-hooks.mjs`, `package.json`)

### The packages on npm, and a conformance CLI (2026-11-04, TIN-612)

- **The packages are renamed `@tineira/apc-protocol`, `@tineira/apc-server`, `@tineira/apc-web` and `@tineira/apc-conformance` (the `@apc` scope on npm is someone else's), and can be published to npm as 0.x pre-releases on the `next` tag.** Every import in `packages/` and the apps uses the new names; V1 keeps its own frozen copies. Each builds ESM and `.d.ts` into `dist/` (tsc build mode, `pnpm build:packages`) with `exports`, `files`, `engines`, repository, MIT, keywords and a README; the workspace keeps using the sources, and only what pnpm publishes points at `dist/` (`publishConfig`), with `workspace:^` becoming `^0.7.0`. `scripts/check-packages.mjs` holds the four to one version that matches `APC_STANDARD_VERSION` (and the tag to `apc-v<version>`), and stops a pack made with npm or without a build. (`packages/*/package.json`, `packages/*/tsconfig.build.json`, `packages/*/README.md`, `scripts/build-packages.mjs`, `scripts/check-packages.mjs`, `scripts/lib/packages.mjs`)
- **A tag `apc-v<version>` publishes them, through npm trusted publishing, with no token.** `.github/workflows/publish.yml` checks the versions and the tag, typechecks, tests and builds, packs the four with pnpm, and runs `npm publish <tarball> --tag next --access public` per tarball. It uses npm 12.2.1, and GitHub's OIDC token (`id-token: write`) with provenance, in the environment `npm-publish`, and only for a tagged commit on `main`. A manual run is a dry run in a job with no OIDC token. The dist-tag is the explicit `--tag next`, since pnpm and npm ignore `publishConfig.tag`. The first version goes out once by hand with `scripts/publish-local.mjs`, which refuses a tree with changes, a HEAD other than `origin/main`, or mismatched versions. The workflow sets no `registry-url` and fails if any npm token is configured (`scripts/check-no-npm-token.mjs`: the environment, `npm config list` and the `.npmrc` files, never printing a value); after that a trusted publisher is set per package on npmjs.com. Each `repository.url` is exactly `https://github.com/tineira/agent-pointed-context`. (`.github/workflows/publish.yml`, `scripts/publish-local.mjs`, `packages/*/package.json`)
- **`npx @tineira/apc-conformance <app-origin> [--grant <mcp-url>] [--revoked <mcp-url>]` checks a live app over HTTP.** It reads `apc.json` (shape, origin, profiles, standard) and, with an agent's MCP URL, checks `initialize`, the core tools and their arguments, the shapes of `get_current_view`, `attention` and `then` (the same in the structured result and the text), `wait_for_focus` timing (900 to 5000 ms for `timeout_s: 1`), an unknown grant's 404 and a revoked grant's 403 answer. It prints PASS, FAIL or SKIP per check, exits 1 on a failure, and has `--json`. What needs the person's page is reported as skipped. It is safe on any URL: https only (`--allow-http` for `localhost`, `127.0.0.1` and `[::1]` literally), no redirects followed, a size cap and a timeout on every request, and no grant secret in any output, even when an answer echoes it. Pulse and Signals in production pass all 11 checks. (`packages/conformance/src/http.ts`, `packages/conformance/src/cli.ts`, `packages/conformance/src/shared.ts`)

### Revoke from the app and open pairing, follow-ups (2026-11-04, TIN-606, TIN-609)

- **Pulse and Signals check the person's consent on their server, not on the page (APC 0.7).** Every dock drop goes to the server; an agent it holds no grant for comes back `consent_required` with a single-use nonce, and only the consent's Allow that sends it back makes a grant, so a page that missed a revoke can no longer pair without asking. A double-clicked Allow pairs once: one drop per agent is answered at a time, the grant is linked only once the hub took it, and the consent's buttons turn off on the first click. (`packages/server/src/consent.ts`, `apps/demo/src/worker/sandbox.ts`, `apps/demo/src/web/App.tsx`, `apps/demo/src/web/hub-consent.tsx`, `apps/signals/src/worker/feed.ts`, `apps/signals/src/web/app.tsx`, `packages/protocol/src/core.ts`)
- **A drop after a revoke in the app, before the dock heard of it, replaces the old line under the app's own id.** The hub asks the old pairing when the same agent pairs again with the same app: revoked, it is replaced; still live, both stay. No more `pulse2` beside a stuck **Revoked by** line. (`apps/dock/src/worker/hub.ts`, `apps/dock/test/revoke-from-app.test.ts`)
- **A revoke is told by the grant's secret, never its id**, so a later grant that reuses an id neither keeps a revoked call running nor answers `revoked` for itself. (`apps/demo/src/worker/sandbox.ts`, `apps/signals/src/worker/feed.ts`)
- **`wait_for_focus` hands over an unread pin within 2 s**: it asks only the pin's app, bounded by `LIMITS.pinLookMs` or its own timeout, instead of every app for up to 6 s. (`apps/dock/src/worker/hub.ts`, `apps/dock/src/worker/trust.ts`)
- **The dock answers right away while an app is slow to take a grant back**: an expired request's grant goes back after the dock's state or `/apc/pair` has answered. An Approve whose approval the alarm already paired now answers ok instead of "withdrawn". (`apps/dock/src/worker/hub.ts`, `apps/dock/test/open-pairing.test.ts`)
- **Dock pages left open from before a deploy reload onto the new code.** The service worker carries a version and takes over at once without touching any page; a dock page (`/dock…`) hears the new worker and reloads itself once, while the landing, `/extension` and V1 at `/v1` never do. Every page checks for a new worker when it comes back into view. (`apps/dock/public/sw.js`, `apps/dock/src/web/sw-reload.ts`, `apps/dock/src/web/main.tsx`, `apps/dock/src/web/request-state.ts`, `apps/dock/test/service-worker.test.ts`)

### Open pairing, with a warning in the dock (2026-11-04, TIN-581)

- **Any APC app can pair with the dock, after the person approves a warning in the dock.** `OPEN_PAIRING` is gone: an app outside `APP_ORIGINS` asks like any other, and its request becomes a pairing only through the warning's Approve (`approve_unverified`; a plain approve is refused as `warning_required`, so an older dock page cannot skip it). The warning shows the domain first and big, **Not verified**, what the app calls itself only as its own word, and the risk ("Your agent will read whatever this app tells it, and that could lead your agent to move data out of your other apps."), with Deny first and focused; it shows once per domain per dock, and a Deny, Unpair or Remove on an unverified app takes the domain's approval back. Verified apps keep their consent flow. (`apps/dock/src/worker/hub.ts`, `apps/dock/src/worker/trust.ts`, `apps/dock/src/web/unverified.tsx`, `apps/dock/src/web/hub.tsx`, `apps/dock/src/web/agent-page.tsx`, `apps/dock/src/web/pet.tsx`, `apps/dock/src/web/dock.css`)
- **A pending pairing nobody decides goes after 10 minutes and frees its place under the cap.** The app gets its grant back, as on a deny; the hub's alarm ends it on time. (`apps/dock/src/worker/hub.ts`, `apps/dock/src/worker/trust.ts`)
- **A kill switch for emergencies.** `UNVERIFIED_PAIRING=closed` refuses new unverified apps and holds every unverified pairing as blocked (never called, shown as **Paused**) until it is `open` again; the blocklist still wins over any approval. Unverified apps carry a **Not verified** badge on the dock's tiles, requests, Float, the pets and the agent's page. (`apps/dock/wrangler.jsonc`, `apps/dock/src/worker/hub.ts`, `apps/dock/test/open-pairing.test.ts`, `apps/dock/test/hostile-world.ts`, `README.md`, `DESIGN.md`)

- **A Deny always wins over an approval still being made, and the dock is never framed.** A yes leaves the pairing `approving` until the hub has introduced itself to the app; a Deny meanwhile (or in any state) removes it, clears the domain's approval and stops every further call to the app, and while an answer is on its way only a second answer of the same kind is held back: Deny stays on while an Approve is on its way or the hub is approving, on every surface including the one that sent it. The approval then turns paired only if nothing holds it (blocklist, kill switch) and the domain's approval still stands; otherwise it is dropped, never stored as paired, and the person approves again. One left half-way is settled by the alarm after a minute. Every removal (Deny, Unpair, removing an agent, expiry) changes storage before it waits on any app, an Approve that ends without a pairing takes back the domain approval it added, and a refused answer is shown in the dock ("Approval was withdrawn; ask again." when another agent's Remove of the same domain withdrew it). Every dock response and asset carries `frame-ancestors 'none'` and `X-Frame-Options: DENY`. An unverified host shows on one line with its registered domain whole, shortened from the left (`…tineira.com.evil.example`). (`apps/dock/src/worker/hub.ts`, `apps/dock/src/worker/index.ts`, `apps/dock/public/_headers`, `apps/dock/src/web/unverified.tsx`, `apps/dock/src/worker/trust.ts`, `apps/dock/src/web/request-state.ts`, `apps/dock/test/open-pairing.test.ts`, `apps/dock/test/request-buttons.test.ts`, `apps/dock/test/health.test.ts`)

### Dock

- **The hub is hardened for apps it does not know, before any can pair.** An app outside `APP_ORIGINS` is unverified and still cannot pair (`OPEN_PAIRING` is unset in every deploy), but every protection for it exists and is tested against simulated hostile apps: its id and tool prefix come from its domain, never from the name it declares (an app calling itself "Pulse" from `evil.example` is `evil_example`); HTTPS on a domain name only, no redirects; a byte cap on every answer the hub reads from any app (1 MiB verified, 256 KiB unverified) and a time limit covering the body; at most 20 app pairings per dock; its results, views, pin and tool descriptions reach the agent marked `untrusted`, with no tool annotations, and its errors carry only the hub's own words; its `then` and `page_open` never count, so it cannot keep the agent waiting; and `BLOCKED_APPS`, a blocklist we operate (empty), refuses a domain (Unicode or punycode) at pairing and stops a pairing with it, shown as **Blocked** on the agent's page and holding no place under the cap. Pulse and Signals pair and work as before, as verified apps.
