## 1. Why this repo exists

The paper describes APC as built into PFA, a private single-owner ledger that is not released. That leaves three gaps this repo closes:

1. **Reproducibility.** A reader can open the hosted demo or run it locally, not only read about it.
2. **Generality.** The paper's own limitation is "one application, one domain, one person". This demo is a second domain (SaaS product analytics) on a second stack, with the same wire format, used by many people at once.
3. **Measurement.** Payload bytes, model tokens against a screenshot, envelope latency, wrong-referent rate and clarification turns are hypotheses in the paper. Here every one of them is instrumented on synthetic data, with no private data anywhere.

It also makes a claim the paper only touches, and which may be the pattern's main advantage (section 3).

## 3. The cross-reference happens in the agent (new)

The person comes to the application **with their own agent**, and that agent already knows things about the person: their files, their other tools, their memory, knowledge the person holds and does not want to give the application. An assistant embedded in the application can only know what the application knows. An external agent pointed through APC brings both halves together **on the agent's side**:

- the application contributes the referent and the facts it holds, bounded by the grant;
- the agent contributes what the person already knows;
- neither hands its half to the other. The application never receives the person's private knowledge, and the agent sees of the application only what its grant allows.

**In the demo.** The application is the analytics product of a fictional SaaS vendor. It knows customers, plans, regions, seats and activity. **It does not know revenue**, and it should not: in the real world revenue sits in the person's billing system or spreadsheet, outside this product. The person's own knowledge is represented by a file `mrr-by-customer.csv` (`customer_id, month, mrr`). The application does not provide it and never reads it; the demo only makes one so anyone can reproduce the scenario. It stands in for what a real user already has.

- **Hosted:** the visitor's browser generates the file from the sandbox's public seed (on V1; the standard's Pulse uses the one fixed world's, `DEMO_SEED`, TIN-621), with a generator that is not part of the server bundle, and offers it as a download. The server has no MRR code and no MRR values.
- **Local:** `pnpm seed` writes it to `user-side/`, a folder no server module references.

**The scenario.** The person drags their agent's mark onto the bar "active customers, March 2026" and asks: *"how much MRR is this, and which customer has the best MRR per seat?"* The pin resolves to `get_figure`, which returns the count and `inputs.customers`, the external ids behind the bar, plus seats per customer. The agent joins those ids with the person's file and answers with the exact MRR and the ranking. No MRR value ever reaches the application.

**Design consequences.**

1. **Join keys are part of the contract.** For the join to work, `inputs` must expose identifiers that exist in the person's other systems (here `cus_0042`, the id their billing also uses), not internal surrogate keys. Each figure in the registry declares which external ids its `inputs` carry. The paper does not state this because in PFA everything lived in one system.
2. **Privacy in the other direction is checked, not assumed.** The seed makes MRR values distinctive. The sandbox records the arguments of every tool call. A canary check that runs **outside the server** (`scripts/canary.mjs`, and the harness in cut 2, both of which have the file) scans that log and asserts no MRR value appears in it, as written, with a thousands separator, or without `.00`. If an agent leaks one into an argument by accident, the report says so. **Boundary:** the log holds the arguments of calls that passed the MCP SDK's schema validation, recorded before the domain validates them (`instrument()` in `apps/demo/src/worker/sandbox.ts`), not every inbound byte. A call the SDK refuses, or a request body that is not a tool call, is not in it, so a clean canary says what reached the tools, not what reached the server.
3. **Scope of the promise.** APC guarantees only what the application learns. What the person's agent does with their own knowledge is between the person and their agent.

## 4. The demo application

**Domain:** product analytics for a fictional SaaS ("Pulse"). Synthetic, seeded, about 200 customers over 18 months, three plans, three regions.

**Data:** `customers` (`id` = external id `cus_NNNN`, name, plan, region, signup month) and `activity` (customer, month, active, seats, usage events) are rebuilt in memory from the sandbox's seed, so a sandbox stores only the seed. That is V1; the standard's Pulse and Signals share one fixed world, the same for every sandbox, and store no seed (§ 12.8, TIN-621). Its Durable Object SQLite holds `grants`, `view_state`, `agent_focus` and `events` (instrumentation).

**Screens:**
- **Overview:** active customers per month (bar chart), the customer bridge for a month (start, new, reactivated, churned, end), seats per month.
- **Plans:** plan × month matrix of active customers.
- **Customers:** a table of rows, and a customer detail pane (plan, seats, usage, status).
- **How to** (the landing page): a six-step walkthrough with the visitor's own URL and file in it: connect, point, ask what it sees or let it wait, a simple example, the MRR example, and what your agents did.
- **Agents:** one MCP URL per agent, "add another agent", "add a restricted agent", the compatibility matrix, the switches (share view, show agent activity) and the event log.
- Every MCP URL shown (Agents, the how-to's connect steps) has its QR beside it; while no agent of the sandbox has connected, Overview and Customers open with a dismissible connect panel (URL, QR, Claude Code command).

**Pin kinds:**

| kind | id | part / params | `next` |
|---|---|---|---|
| `customer` | `cus_NNNN` | `plan`, `seats`, `usage`, `status` | `get_customer` |
| `figure` | — | `{ key: active_customers, month, plan?, region? }` | `get_figure` |
| `figure` | — | `{ key: customer_bridge, month }`, part `step:<start\|new\|reactivated\|churned\|end>` | `get_figure` |
| `figure` | — | `{ key: plan_matrix, month }`, part `cell:<plan>\|<month>` | `get_figure` |
| `figure` | — | `{ key: seats, month }` | `get_figure` |

**Per-kind allowlist (v0.2.0).** The protocol's `parseTarget` checks the grammar only: any token-shaped params pass it, on any kind. The host narrows it per kind in `checkPin` (`apps/demo/src/worker/domain.ts`). A `customer` pin is named by its id and part alone and carries no params: anything but absent or `null` is `invalid_target`, so a value like `{"note":"SECRET-1234.57"}` is never stored, logged or handed to an agent in `focus.params`. A `figure` pin keeps only the keys its figure's `parse` reads (`only()` in `apps/demo/src/model/figures.ts`); any other key is `invalid_target`. A protocol test documents that the parser alone does not do this, so the host check stays.

## 5. Sandboxes and connection

**One sandbox per visitor.** Opening the demo creates a sandbox: one Durable Object with a random id, kept in a cookie, seeded with its own synthetic data (on V1; on the standard's deploy every sandbox shows one fixed shared world and keeps only the visitor's own state, § 12.8, TIN-621). It holds that visitor's pins, presence and event log, and expires after a few hours of inactivity (alarm, then delete). Visitors never share state: a URL leads to exactly one Durable Object.

**One secret MCP URL per agent grant.** By default a sandbox has one grant with full access, shown on Connect as a URL to paste as a connector in any MCP client (`https://<demo>/mcp/<sandbox>/<grant-secret>`). No login: the secret in the URL is the grant. "Add a restricted agent" creates a second grant limited to one region, with its own URL, to show C5. Each grant gets its own mark on screen.

**Rate limits** per sandbox and per IP keep the hosted demo cheap and stop one visitor from affecting another.

## 6. Wire format

The same as `04-payload-specification.md` (view result, focus payload, `attention` envelope, `wait_for_focus`, presence message, switches). Differences:

| PFA | Demo | Why |
|---|---|---|
| Postgres + RLS | Durable Object SQLite per sandbox; grant checks in one module | isolation by construction, no accounts |
| Supabase Realtime Broadcast | WebSocket from the sandbox's Durable Object to its page | one place holds the state and the channel |
| `wait_for_focus` ceiling 50 s (host limit) | configurable, default 50 | keep the paper's number, allow a measurement without it |
| OAuth 2.1 + PKCE | secret capability URL per grant | any MCP client connects by pasting a URL; OAuth can come later |
| `attention` as a top-level key of the structured result | the same, **and** mirrored in the text content | some clients show the model only the text content |
| bank-text hashing (`h:<16 hex>`) | not needed: no free-text keys in this domain | kept in the library, unused here |

**Waiting after answering (TIN-95, 2026-10-17).** The stance moves from "a timed-out wait is the exception" to "wait after every answer while the person is on the page, gated by presence". Agents answered and stopped, so the person had to ask whether a pin had arrived. Now `APC_INSTRUCTIONS` and the tool descriptions say to call `wait_for_focus` after answering. While the sandbox holds at least one open page WebSocket (`pageOpen()` in the host context), every tool result carries a model-visible `then` key next to `attention`, placed the same way (structured result and text, never `_meta`). With no page open the key is absent, and `wait_for_focus` returns at once with `{ focus: null, timed_out: false, page_open: false, note }`. It checks the pin row and presence on every poll, every 2 s (`pollMs`), and returns that same result early when the page closes; "at once" means at its next check, so within 2 s of the close the sandbox sees. A timeout returns `{ focus: null, timed_out: true, page_open, note }` without `then`, so the loop ends there. The default timeout is 25 s, and the server stays passive: no push, no session, no new storage. **Ceiling, measured** (`scripts/wait-ceiling.mjs`: a fresh sandbox, its page socket held open, no pin). The local Workers runtime (`pnpm dev` with the ceiling raised to 600 for the probe) held waits of 30, 50, 60, 90, 120, 180 and 300 s to within 0.1 s. The 600 s probe was cut at 304.5 s by the probing client's own 300 s header timeout (Node's fetch), not by the runtime. On production (apc.tineira.com, deployed ceiling 50), 30 s and 50 s held (30.3 s, 50.3 s). Cloudflare documents no wall-time limit on a Durable Object request while the caller stays connected. The ceiling stays at 50 s anyway, because the client is what limits it: the MCP TypeScript SDK's default request timeout is 60 s, and in the end-to-end run Claude Code 2.1.302 cut a 300 s wait at about 60 s. Adoption is measured per agent as `waits_after_answer` in the compatibility matrix: a `wait_for_focus` that starts within 30 s after the grant's last call ended, when that call was not itself a wait. **Known gap:** under `pnpm dev`, closing a Chrome tab did not reach the Durable Object through the Vite dev proxy. The socket stayed open there, so `then` kept coming and the agent waited once more, which the timeout bounds. A scripted page socket that is closed, or whose process is killed, is seen as closed at once. A page heartbeat would close the gap. **Closed by the heartbeat (TIN-95 follow-up):** the page sends `"ping"` every 30 s on its WebSocket, and the sandbox answers `"pong"` through the hibernation API's auto-response, which does not wake the object and never reaches the log or the presence channel. `pageOpen()` counts a socket only while it is OPEN and was answered, or accepted, within 75 s (two heartbeats plus slack for throttled background tabs; `apps/demo/src/worker/page.ts`). The 75 s window is the fallback for a proxy that never reports a closed socket: where the close does arrive (a scripted socket that is closed or killed), the socket stops counting at its next check. Under `pnpm dev`, a closed Chrome tab now reads as closed 67 s after the close.

**With view sharing off, attendance is hidden too (v0.2.0).** With `share_view` off the person has asked not to be observed. Until v0.1.0 the view went dark but `then` and `page_open` still told every grant, a restricted one included, that a page was open and when it closed: the paper's Table 2 now lists that as a channel with no switch. Now the switch covers it. The sandbox's `pageOpen` callback returns `null` while sharing is off (`attendance()` in `apps/demo/src/worker/page.ts`), so no result carries `then` (`then_bytes` logs 0), and `wait_for_focus` waits for a pin for its full timeout and returns the pin when one arrives, but reports no `page_open` at all, neither true nor false, and does not end early when the page closes (`packages/server/src/tools.ts` already omits the key and skips the early return when the callback yields `null`). Pointing still works with sharing off; only attendance is hidden. The tool description, `APC_INSTRUCTIONS` and the manual say that `page_open` is reported only while the person shares their view. With sharing on, nothing changed.

**The manual, opt-in (TIN-96).** Beyond what the server tells every agent, the full manual exists in two opt-in forms with one text, both loaded by an explicit gesture of the person: the MCP prompt `guide` (a slash command or a menu item in the client) and the installable skill `skills/pulse-agent`. Whether a grant loaded the prompt is a column of the compatibility matrix.

## 7. Architecture

A pnpm monorepo with three reusable packages and one app, so the pattern can be adopted, not only watched:

- `packages/protocol` (`@tineira/apc-protocol`): the wire types and the target grammar (kinds, parts, key-only params, canonical keys, `data-focus` attributes), shared by both sides.
- `packages/server` (`@tineira/apc-server`): runtime-agnostic TypeScript. The `attention` envelope (structured result and text), the `get_current_view` and `wait_for_focus` tools over a host-supplied context, the presence event builder. The view allowlist and the figure registry are the host's (here `apps/demo/src/worker/domain.ts` and `apps/demo/src/model/figures.ts`).
- `packages/web` (`@tineira/apc-web`): framework-agnostic DOM. `data-focus` attributes and their parser, drag-to-pin with the innermost-target rule, a hit-test registry for canvas or SVG surfaces, agent marks and the presence cursor, view reporting (debounced, visible tab only).
- `apps/demo`: Pulse. A Cloudflare Worker (Hono) routes to the sandbox Durable Object, which serves MCP over Streamable HTTP (official SDK), the browser API and the WebSocket. The front end is Vite + React, served as Worker static assets. The figure functions live in `apps/demo/src/model/` and are imported by both the page and the Durable Object: that is what C4 tests. Since TIN-604 `apps/demo` is Pulse for the APC standard (pulse.apc.tineira.com); V1, the Pulse this section and the paper describe, is frozen in `apps/v1` (apc.tineira.com/v1) with its own copy of the three packages in `apps/v1/src/apc` (§ 11).

## 8. Instrumentation

Every event goes to the sandbox's `events` table, exportable as JSONL:

- `tool_call`: grant, client name, tool, arguments bytes, result bytes, envelope bytes (0 when none), server latency.
- `tool_call` also logs `then_bytes`: what the loop hint added (0 when no page was open, or when the person does not share their view). The two are measured apart. `envelope_bytes` is the compact JSON of the `attention` object alone (`{"focus":…,"note":…}`), without the key or the delimiter around it. `then_bytes` is the text `,"then":"…"` that the hint adds to a result's text, key and delimiter included. **Payload:** on apc.tineira.com the envelope for a pin on a monthly bar of `active_customers` is 571 bytes (its `part_note` is the longer one), and 539 for the `churned` step of `customer_bridge` (it moves by a few bytes with the step name and the origin's length). While a page is open and the view is shared, `then` adds 117 bytes to every result's text and the same to its structured result.
- `pin`, `envelope_delivered`, `seen`, and `next_read` (the first call to `focus.next` with `focus.next_args`).
- `inbound`: the arguments of every tool call that passed the SDK's schema validation, recorded before domain validation, for the canary check (section 3, which states the boundary).

Derived metrics, shown on a sandbox metrics page and exported for the paper: focus and envelope payload bytes; pin → envelope → seen → next-read times; the share of pins read through the envelope vs `get_current_view` vs `wait_for_focus`; canary hits (expected 0). The hosted demo also keeps anonymous aggregate counters (sandboxes, pins, clients) and nothing else.

## 9. Tests and verification

**Automated (the tests the paper describes, done here):**
- **Registry completeness, both directions:** a static scan of every `data-focus` usage in the app against the figure registry. Every key and part used is registered, and every registered key is used.
- **Equality:** on a fixed fixture, `get_figure` returns the same values the page's model computes, for every figure key.
- **Envelope:** present only while `pinned_at > seen_at`; gone after the acknowledging read; a new pin replaces an unread one; mirrored in the text content.
- **Grants:** a restricted grant cannot be pinned outside its region; figures are cut and counted; a by-id screen outside the grant is `view: null`.
- **Isolation:** one sandbox's URL never reads, pins or hears another's.
- **Content-free channels:** the presence message type has no content field; the view and pin refuse amounts and free text.
- **C7:** no server module references `user-side/` or the MRR generator; the canary is 0 after the scripted scenario.

**Client compatibility matrix (C8).** Recorded automatically per agent from the event log (`apps/demo/src/worker/compat.ts`, shown on the How to and Agents pages and served as `compat.json`): client name, version and user agent from `initialize`, tool list, pins, envelopes, how each pin was read (`get_current_view` or `wait_for_focus`, and whether after an envelope), whether the pin's `next` call was made, and the median time from pin to read. One URL per agent keeps each client apart. Run by hand over every MCP client available to the author (Claude, Codex, Cursor, Grok, Grok bot, AGY, others as they come), one row each: connects to the remote URL (directly or through `mcp-remote`); the model sees the envelope; the model calls `get_current_view` on "this"; the pin resolves through `next`; the MRR join is answered. Published with each release.

## 9b. Capacity (measured 2026-10-15, production)

Each visitor is its own Durable Object, so concurrency is not shared: nothing serialises one visitor behind another. What bounds the hosted demo is the Cloudflare plan's quotas and its CPU limit per request.

**Load test** (`scripts/loadtest.mjs`, one client in Santiago): every simulated visitor opens a sandbox, reads its state, reports a view, connects an agent over MCP (initialize, tools/list), pins a figure, makes an unrelated call that carries the envelope, reads the view and follows `next`, and reads the matrix.

| Visitors at once | Requests | Errors | p50 per request | p95 per request |
|---|---|---|---|---|
| 20 | 220 | 0 | 240 to 630 ms | up to 2.1 s |
| 75 | 1,650 | 0 | 230 to 570 ms | up to 1.5 s |
| 150 | 3,300 | 0 | 240 to 650 ms | 0.9 to 3.6 s |

The p50 is mostly network (Chile to the edge to the sandbox): inside the Durable Object an MCP call took about 24 ms of wall time. The 150-at-once p95 coincides with 150 sandboxes created in the same seconds.

**CPU per invocation** (from `wrangler tail`, sampled): median 1 ms on almost every route, p95 about 10 ms, maximum 17 ms; 2.8% of invocations were over 10 ms, the Free plan's limit, and none failed. The heaviest were downloading the dataset (since removed: the page rebuilds it from the seed with the same function) and MCP calls, which build the SDK server per request (7 to 11 ms).

**Changes from the test:** the compatibility matrix reloads on the sandbox's WebSocket announcements instead of polling every 5 s (one open how-to tab went from about 1,440 Durable Object requests an hour to a handful); the page rebuilds the data from the seed; the WebSocket reconnects with backoff; rate limits of 10 new sandboxes a minute per IP and 300 calls a minute per sandbox (page and agents together; per sandbox, not per IP, because hosted agents share egress IPs). Cloudflare's limiter is approximate: in a test it started answering 429 after about 30 creations in a minute.

**Remaining:** MCP calls rebuild the SDK server per request; caching it per grant would cut their CPU. On the Free plan the daily quota (100,000 Worker and 100,000 Durable Object requests) is the ceiling, roughly 1,000 visits a day; the Paid plan removes it for a few cents per thousand visits.

## 10. Cuts

1. **Cut 1, the demo runs end to end**, hosted and local: sandboxes, view, pin, envelope, `wait_for_focus`, presence, the four figures, the MRR join scenario, instrumentation, the tests and the client matrix in section 9. README with a two-minute walkthrough.
2. **Cut 2, the evaluation harness:** a scripted agent over the Claude API on one fixed question set, four referent conditions (describe in words, paste the deep link, screenshot plus the same tools, APC) × with and without the user's file, same tools and grant in every condition. Measures: input and output tokens, clarification turns, wrong-referent rate, answer correctness against seeded ground truth, payload bytes reported apart from tokens.
3. **Cut 3, release:** repo public, first Zenodo software DOI, paper v2 citing the release for its measurements, adding C7 and the client matrix.

## 12. APC v2: one agent across apps (TIN-371)

*Naming (2026-11-03, TIN-605): "APC v2" is the name this section was written under. What it describes is now just the APC standard, with no version in what a person reads, at apc.tineira.com (dock), pulse.apc.tineira.com (Pulse) and signals.apc.tineira.com (Signals); V1, the paper's demo, is frozen at apc.tineira.com/v1. The earlier hosts with a `v2` label and the Workers named after them are gone: the Workers are `apc-dock`, `apc-pulse` and `apc-signals`, with fresh Durable Objects. The text below keeps the historical names where it records what was decided then.*

**The idea.** A window on the desktop, the dock, holds the person's agents, already connected. The person drags one onto anything in any APC app, in any window, and it is Pulse again: the agent is pointed at that thing and reads it with its own access.

**Two options.**

| | (a) Dock as launcher | (b) Dock as attention hub |
|---|---|---|
| Agent connects to | every app, one MCP URL each | the hub, once |
| Waits | one `wait_for_focus` per app | one, across all apps |
| Data path | agent to app, direct | agent to hub to app (relayed) |
| New on the wire | nothing | hub tools, an app reference on the focus |
| Dock knows where an agent points | no | yes |

**Choice: (b), the attention hub.** Three reasons.

1. A drop cannot hand an agent a URL. MCP clients add servers by configuration; whether any lets a connection be added mid-conversation must be verified. So (a) is v1 with one paste per app, which we already have.
2. A tool call blocks the agent's turn, so it holds one wait at a time. With N apps, a pin in another app reaches it only on its next call there.
3. The dock must show and revoke where each agent is pointed (12.5). Only a dock in the path can.

The cost of (b): app results pass through the hub, so a real hub runs where the person already trusts (their machine or their own account). The hosted prototype is fine because Pulse is synthetic. The hub stores no results and logs sizes and presence only.

### 12.1 Pairing without secrets in the drag

The drag carries a public handle and a short-lived ticket, never a grant:

```ts
// dataTransfer type "application/x-apc-agent" (APC_AGENT_TYPE), set on dragstart in the dock.
// TIN-369 shipped { v: 1, agent }; hub and ticket join it with pairing (TIN-370), and the parser ignores keys it does not know.
interface AgentDrag {
  v: 1;
  hub: string;      // the hub's origin, e.g. "https://apc.tineira.com"
  agent: string;    // public handle, "ag_7f3k…"; safe for any page to read
  ticket: string;   // single use, 60 s, bound to this agent; opens a pairing request, nothing else
}
```

A page sees only the types during `dragover` and the data on `drop`, enough to light up targets. Whether custom types survive a drag between browser windows, or from a native window, must be verified per browser and OS.

On drop, the app looks up `(hub, agent)`:

- **Paired:** it stores a v1 pin for the grant it gave that agent. Nothing else changes.
- **Not paired:** the app asks for consent on its own page ("Let *agent* from *hub* read Pulse? Full or one region?"). On yes, it creates a grant (v1 `addAgentGrant` or `addRestrictedGrant`) and sends the grant to the hub over a back channel, server to server: `POST {hub}/apc/pair { ticket, app: { id, name, origin, icon }, mcp_url }`. The hub then asks in the dock: "*app at origin* wants to be read by *agent*. Allow?" The pairing counts only when both sides have said yes. The dock shows the origin of `mcp_url`, because that is where the tools come from.

The look-up is the app's server's, not its page's (APC 0.7, § 14): the page sends every drop there, and an agent with no grant comes back `consent_required` with a nonce that the consent's yes must send back.

A local hub (extension, desktop app) cannot take that POST; the app's page would hand the grant to the extension, and how a page reaches an extension it does not know must be verified (`externally_connectable` takes a static list of sites). The long-term answer is MCP's own authorization, OAuth 2.1 with PKCE, with the hub as client and the ticket only starting the flow. v1 deferred OAuth (section 6); v2 brings it in.

### 12.2 Focus from app to hub

v2 reuses the v1 pin as it is. Each `(agent, app)` pair is one v1 grant held by the hub, so the app stores `FocusRow` per grant, resolves `FocusPayload` and trims it to that grant exactly as today. C5 holds per app.

The hub learns about pins with v1's own tool. While the dock is open, the hub keeps one `wait_for_focus` running against each paired app, so the hub does the N waits and the agent does one. A wait that returns `page_open: false` comes back at once, so the hub backs off for that app (one retry every 15 s) instead of spinning. Once the dock closes, the hub stops watching.

The app's `seen_at` now means "the hub received it"; the hub logs the agent's own `seen`.

Not built: an optional doorbell would cut latency and held requests. After a pin, the app's server would send `POST {hub}/apc/ring { app, agent }` with a token from pairing. It would carry no target; the hub would read the focus as before.

### 12.3 Tool names and the app on the focus

The hub exposes its own `get_current_view` and `wait_for_focus`. It hides each app's two, and relays the app's other tools as `<app>__<tool>` (`pulse__get_figure`). The app id is `[a-z0-9]{1,16}` and unique per hub, chosen at pairing, with a suffix on collision. The total stays within 64 characters, because client name limits vary and must be verified.

A new app changes the tool list: the hub sends `notifications/tools/list_changed` and sees whether the client lists again. Until then `call_app_tool({ app, tool, args })` always works.

The focus says where it came from:

```ts
interface AppRef { id: string; name: string; origin: string }
// FocusPayload gains (optional): app?: AppRef
// next / next_args are rewritten by the hub:
//   "pulse__get_figure", { … }                                          when the client has the prefixed tool
//   "call_app_tool", { app: "pulse", tool: "get_figure", args: { … } }  otherwise
```

Relayed results arrive with the app's own `attention` and `then` keys, which point at tools the agent cannot see. The hub strips them and attaches its own. The hub's `get_current_view` returns the focus plus `views: Array<{ app: AppRef; view: ViewPayload | null }>`, newest first.

### 12.4 Presence and attention: per hub

An agent has one mark, so one focus: the newest pin across apps wins, as in v1. Older pins stay drawn in their apps; the hub no longer surfaces them.

`attention` rides on every hub result while the hub's focus is unread. `then` is per hub: it is present when the dock is open and at least one paired app reports `page_open: true`. If every app reports `null` (none shares its view), `then` is absent and `page_open` is not reported, as in v1. The dock is the drag source, so with the dock closed nobody can point.

Presence events keep `v: 1` and gain an optional `app`. The app's own presence works unchanged: the relayed call reaches it under that agent's grant.

### 12.5 Security: a dropped agent points, it never grants

What a hostile page can do with a dropped agent:

- read the handle and an unexpired ticket, and ask to pair; the person sees the request in the dock and can say no;
- once paired by the person, pin keys (checked by `parseTarget` and the app's allowlist) and offer tools whose descriptions and results may try injection, as any MCP server the person adds can; the hub never merges an app's `instructions` into its own;
- pull the agent's attention; the hub rate-limits pins per app (v1's 300 a minute) and the dock shows each one.

What it cannot do: get the hub's URL or any grant, see another app's view or focus, call its tools, or receive what the hub relays for it. An app outside the hub's list is held to more (section 15): named by its domain, size and time limits, its output marked untrusted, and a blocklist. The agent may still carry data from app A into arguments to app B: the C7 boundary (section 3), now between apps. Presence in the dock makes it visible, not impossible.

**The dock shows**, per agent, where it points now (app, origin, `kind:id`, part), its paired apps with last activity, and pending pairings. **It revokes**: clear the pointer, or unpair an app. Unpairing is authoritative at the hub: it deletes the grant, stops relaying and drops the app's pins. The app revokes on its own side too, from its agent bar, without the hub (section 14).

### 12.6 Where the dock lives

- **Web window** (or PWA) at apc.tineira.com/dock (since TIN-420; / is the APC v2 landing, and the Worker sends a visitor whose cookie holds a dock on to /dock with the query kept), hub in a Durable Object per dock. No install; needs apps that accept native drops (TIN-369); cannot float on top (Document Picture-in-Picture might; dragging out of it must be verified). Each agent has its own page at /dock/agents/<id> (TIN-419): what it did (a log of its last 300 calls through the hub: tool, app, time, the pin it read, error code; never argument values or results), its apps with Unpair and pending requests, its connection folded, and Remove.
- **Browser extension.** A content script can add drop handling to any page; native messaging reaches a local hub. Section 13 settled that the extension only receives drags, from the dock and Float. Costs an install, store review, one build per browser.
- **Desktop app** (Tauri or Electron). A natural home for a local hub, the heaviest to build. OS drags into browsers may keep only `text/plain` and `text/uri-list` (to verify).

**Order:** web window first, extension second, desktop app only if the extension cannot start drags.

### 12.7 Changes to the packages

Everything below is **additive and opt-in**, so v1 stays on 0.2.

**Breaking, and avoided:** prefixing tool names inside apps, keying `FocusRow` by app, or requiring OAuth instead of the secret URL. Any of these would make it APC 0.3.

## 13. A browser extension: the agent on any page (TIN-395)

**The idea.** Most pages the person reads will never implement APC. The person keeps dragging their agent from where they already do: the dock window or **Float**. A browser extension makes every page able to **receive** that drag. On an APC app, the extension stays out of the way and the app takes the drop as it does today. On any other page, the extension reads what the person pointed at and hands it to the agent through the dock's hub. The extension is not a drag source: it has no side panel and no agents of its own.

### 13.1 What the spikes settled (2026-10-26)

The spikes are throwaway: an MV3 extension (a content script on every page, a service worker) and a fake hub, a Durable Object under `wrangler dev`. The first round ran in Chromium 134, because Chrome 156 ignores `--load-extension` (branded Chrome dropped the flag) and Edge 156 ignored it once it had signed the scratch profile in to sync. The later rounds ran in Chrome 156 and Edge 156 on fresh profiles, with the extension loaded over the DevTools Protocol: `Extensions.loadUnpacked`, which needs `--remote-debugging-pipe` and `--enable-unsafe-extension-debugging`. Phase 1's automated tests can load it the same way.

**From the dock and from Float (Chrome 156 and Edge 156).** The dock was the real one at apc.tineira.com/dock, in its own window, with a test agent connected so its tile dragged the APC payload. The extension marked a drag that started in the dock's own document, which tells a drag from the dock window apart from one from Float, a separate document.

| Drag from | onto a plain page | onto Wikipedia | onto an APC app |
|---|---|---|---|
| the dock window | received | received | the app took it, the extension stood back |
| Float (Document Picture-in-Picture) | received | received | the app took it (Edge) |

The payload arrived whole, with the real hub (`https://apc.tineira.com`). So Float's open question in 12.8, whether a drag out of it lands in a tab, is answered: it does.

**Match the dock's drop effect.** The dock drags a connected agent with `effectAllowed = "link"`, and `@tineira/apc-web` answers `dropEffect = "link"`. A content script that answers `copy` makes the browser refuse the drop: the person sees the not-allowed cursor over the page, and `drop` never fires. That was the spike's first run. The extension answers `link`, as the apps do. The not-allowed cursor over the dock itself, where a drag starts, is expected, since the dock takes no drops.

**Earlier rounds** dragged from a test side panel, before the extension stopped being a drag source. What they showed still holds:

- **Feedback is required.** With nothing drawn on `dragover` or `drop`, drops that landed looked like failures. So the content script highlights the target while an agent is over the page and confirms the drop.
- **No `text/plain` on a connected agent's drag.** With it, a drop on the tab strip made the browser search Google for that text. The dock's connected drag already carries none. The only `text/plain` drag stays the not-yet-connected agent's connect prompt (TIN-408).
- **An APC app keeps its drop.** The content script listened on `window` in the bubble phase, and when the page had handled the drop (`defaultPrevented`), the extension did nothing. That changed since: the extension now leaves an APC app alone by what the page is, not by what it did with the drop (TIN-476), and takes every other page's drop first (TIN-573, 13.2).
- **Other windows and other browsers.** A drag landed in a torn-off window of the same browser, and across browsers (Chrome into Edge and back), each drop carrying its own hub.
- **The drop point needs choosing.** A drop on a margin fell back to `<html>`, `<body>` or a whole `<section>`. A reading comes from the nearest block element, and a drop not on one reads only the title and address (13.2).
- **The service worker cannot hold a channel.** It stopped after exactly 30 s with no traffic, closing its WebSocket with 1001, in all three browsers. With a hub ping every 20 s it stayed up for more than 5 minutes. So the extension holds no channel at all: a drop wakes the service worker, which pushes the reading and is done.

Not verified: drags from the dock or Float on macOS and Linux.

### 13.2 Two kinds of target

- **An APC app** handles the drop itself: `enablePinning` calls `preventDefault()`, then pairs and pins as in section 12. On an APC app the extension reads nothing and pins nothing: no outline, no reading, no pin (except on a Direct-only app that would lose the drop, which it answers with how to connect directly, § 17). It first stepped back only when the app had taken the drop, and moving Pulse's own pin left a second pin from the extension (TIN-476). A page is an APC app by the standard's own marks only (`isApcApp` in `drop.ts`, checked at each drag since these apps render after load): the agent bar `apc-agents`, an agent mark `[data-apc-mark]`, or `data-apc-native-drops`, which `enablePinning` sets on the root as it mounts, before the bar has loaded. Pulse and Signals mount `enablePinning` with their profiles before their state loads and render `<apc-agents>` once it has. It used to be `data-focus` too, but that name is generic: an app may use it for its own rows and some UI libraries set it on whatever has focus, and such a page lost every drop, since nobody answered the `dragover` (TIN-703). A drop nothing on an APC app takes (a drop on its text outside any target) is no longer refused in silence: the extension's `dragover` listener runs after the app's (below), and when the app left a `dragover` unanswered, the extension takes it and answers the drop with the card of § 17 at the drop point: "This page did not take your agent here. It is an APC app: drop your agent on something it highlights. Nothing was sent." Nothing is read or sent there. It decides at the drop point as well, by the app's own rule (`appTakes` in `drop.ts`, the same steps as `targetOf` in `@tineira/apc-web`, with the protocol's `parseFocusAttrs`): from the element at the drop point, the nearest `[data-focus]` that parses as a target (`kind:id`; an empty, `"true"` or other generic value is skipped), never across a shadow root. When the app would pin there, the extension shows no card, whatever the last `dragover` said (the two can be split by a fast release; found by review on #142). A first version took any `[data-focus]`, across shadow roots, as the app's, and so stayed silent on drops the app did not take (fix check on #142). Other pages that take drags for their own sake (X does, for attaching files) are not APC apps: stepping back there refused the agent (TIN-472), so the extension takes the agent's drop and answers `link` whatever the page did. The last handler to answer wins, and Grok's, added after the extension's, set `none` on every `dragover`, so the browser refused the drag and no `drop` fired, with the outline still showing (TIN-572). The extension now moves its `dragover` listener to the end of `window`'s list when a drag with the agent arrives (`dragenter`) and on each `dragover`. Its `drop` listener ran in the bubble phase on `window`, so a page that stopped `drop` on `document` or `body` kept it from the extension. It now runs in the capture phase on `window`, and the content script runs at `document_start`, before the page's own scripts, so its capture listeners (`dragenter`, `drop`) come first in `window`'s list (TIN-573). The page's own handlers still see the drop after it.

  How a page can still win, so nobody reads this as a guarantee: (1) stopping `dragover` before it reaches `window` (`stopPropagation` on `document`, `body` or the element under the pointer) while answering it with `none`: the extension's answer never runs, and the browser refuses the drop; (2) a `dragover` handler on `window` that re-adds itself each time it runs, or one added between the extension's last `dragover` and the drop, which answers after the extension's and refuses it; (3) in a tab the content script was injected into later (one already open when the person granted the site or installed or updated the extension), a capture listener the page added on `window` before it, which can stop `dragenter` and `drop` with `stopImmediatePropagation`. A lost `dragenter` costs little, since each `dragover` moves the listener too; a lost `drop` is a drop that does nothing. A reload ends (3).
  **Frames (TIN-752).** A dashboard is often a frame from another origin (Datamind's Tableau view: `iframe#tableau`, whose address starts on the site and redirects to Tableau). Drag events over a frame go to the frame's document, never to the page around it, so a content script in the top frame alone never saw them, nobody answered `link`, and the browser refused the drop. The content script now runs in every frame Chrome lets it into (`allFrames: true`, and `matchOriginAsFallback: true` for `about:blank`, `srcdoc` and `blob:` frames, which count by the origin that made them; with it Chrome refuses a registration whose patterns have any path but `/*`, so only whole-host grants are registered, `scriptMatches`), and tabs already open get it in every frame too. Each frame takes the drops that land in it, in its own coordinates: the browser sends a drag to the innermost document under the pointer, so exactly one frame acts, the outline and the pin are drawn in that frame's document, and the service worker answers the frame the drop came from (`sender.frameId`; a later word goes with `chrome.tabs.sendMessage(tab, msg, { frameId })`, `replyTarget`), never every frame of the tab. A reading from a frame carries the frame's address, where its text came from (an `about:blank` or `srcdoc` frame of its parent's origin gives that origin), and as its title the tab's title, which the person sees, then the frame's own when it differs (`frameTitle`). Consent (13.3) is the tab's site, the one in the address bar, and the card's answers are kept for it; inside a frame the card names it ("Always on *datamind.cl*", "Not on *datamind.cl*"). A frame's own origin adds two exceptions (`frameConsent`): a sensitive domain, or a site the person set to Always ask, makes the drop ask every time, and a site set to Not here sends nothing. The card that then asks every time names the site whose setting or domain it is (`askingSite`): the frame's host when the mark is the frame's, the tab's otherwise. A frame with an opaque origin (sandboxed, `data:`) has no address a reading could name: a drop there says "This part of the page has no address of its own, so your agent cannot read it: nothing was sent.", and the service worker never parses an origin it cannot (`originOf`). A frame the extension may not enter has no content script, so the extension cannot see a drop there at all: the top frame notices the agent leaving its own document for a frame, waits 400 ms for a frame with the content script to say it has the drag (through the service worker), and otherwise asks the service worker about the frame under the pointer (`runtime.getFrameId` of the frame element, looked up in the tab's frames, `frameOutside`): only when that frame is outside every grant does it say, in its corner, "This part of the page comes from *tableau.example.com*. Allow this site again in the APC extension to include it." It names a host only for that frame; when Chrome cannot tell which frame it is, it says "another site", and only if some frame of the tab is outside. A note already shown goes as soon as a frame with the content script says it has the drag. The extension e2e does not check that note: the page around an out-of-process frame gets no `dragleave` for a drag sent through the DevTools Protocol. A grant for a page on a port of its own (the popup's `http://host:8080/*`) covers that port only, as Chrome matches it, so a frame on another port of the same host is asked for too; a pattern with no port covers them all.

- **Any other page** gets a **page reading**: what the person pointed at, taken by the extension and delivered as data. It is a different trust model from a pin. A pin names a target that the agent then reads through the app's own tools, with the access the app granted. A reading is the text the extension saw, nothing more, with no tools behind it. So the dock and the agent's results call it a reading, not a pin, and draw it differently.

A reading holds:

- the page's origin and path (no query string or fragment, which often carry tokens) and its title;
- the nearest block element at the drop point (a paragraph, list item, cell, heading, quote, link, button, label or legend) that has text the person sees; otherwise, on pages built of divs and spans such as X (TIN-472), on a photo, or under a link stretched over a card to make all of it clickable, whose words are only for screen readers (TIN-697), the nearest box going up with 16 characters of text or more, or a list, grid or table item (`article`, `li`, `figure`, `tr`, `role=article`, `listitem` or `row`) with any, so an empty cell gives its row, taking the card itself when its wrappers hold the same text, and never a box that is most of the page (`blockAbove` in `read.ts`): its role, its `aria-label` or `title`, its visible text (up to 2 KB), and the heading it is under (`headingOf`): the heading it is in, else its own first heading (a card's title), else the nearest heading before it, h1 to h6 or `role=heading`, never one inside an item, `section`, `aside` or `nav` it is not in, and on leaving one it is in, that one's own first heading, so a card in a grid is never put under the card before it;
- in a table cell, the column header and the row's first cell (`apps/extension/src/read.ts`);
- the person's selection, if any (up to 2 KB), and where it is when that is not the pointed block: the heading it is under and its block's text (up to 500 characters). Inside the pointed block it adds nothing, since the block and its heading are already there (TIN-571);
- every form control the person can see inside the outline, with its label and what was typed or chosen in it (TIN-571, TIN-619), below.

**The outline is the scope and the consent (TIN-619).** While the person drags, the extension outlines what a drop there would read (`scopeOf` in `content.ts`), and the drop reads exactly the element that was outlined when the agent was let go (a moved pin too), never what is under the pointer by then: nothing outlined reads only the page's title and address and the selection, and an outlined element the page took out of the document before the drop sends nothing and says "The page changed what was outlined: nothing was sent. Drop again." (a first version hit-tested again there, so a page could swap in a whole form after the person saw a paragraph outlined; found by review). The outline is:

- on a form control, its **card**: the largest box around it that holds no other control (a radio's whole group counts as one) and at most 1,200 characters of text (`cardOf` in `read.ts`): a field with its label, or a Google Form's question;
- on the label of a control (a `label`'s control, a `legend`'s fieldset, or a control that names the block or an element in it in `aria-labelledby`, as a Google Form's answer names its question's title), that control's card, when the box around both holds no other control;
- on a chart's mark (TIN-760), that mark: a point of a line chart or a bar, drawn in SVG, as below;
- otherwise the nearest block of text, as before; a drop on a form's own margin outlines the whole form.

**Chart marks (TIN-760).** A dashboard's charts are often SVG with no text at their points. On Datamind's Highcharts, a point is a `path.highcharts-point` with no `aria-label`, `<title>` or `data-*`, and the content script's isolated world cannot see Highcharts' objects. So the nearest block of text was the whole chart, and the outline, the pin and the reading were all the chart's. Now a drop on a mark of a **confirmed chart** outlines and pins that mark (`markAt` and `readMark` in `content.ts`).

- **A confirmed chart** (`chartAxes` in `chart.ts`) is a drawing with a value axis (two numbers or more in one aligned line) and either a category axis (two labels or more in a line the other way) or data labels. Outside a confirmed chart no shape is a mark, even one with an `aria-label` or `<title>`, so an icon, a checkmark or a control drawn in SVG reads as it did. For the same reason a pie slice or a map shape, which has no axes, is not a mark here.
- **A mark** is a filled shape (`path`, `circle`, `rect`, `ellipse`, `polygon`) the person sees, at most a quarter of its drawing. It is not in anything whose class names an axis, grid, legend, label, title, tooltip, background, navigator, scrollbar, crosshair, plot band or plot line. It is not itself a tracker, hover halo, area fill or line graph. And it does not span most of the plot's categories, which a plot band or an area's fill would. Highcharts' points meet this generic rule.
- **Finding it:** the elements at the drop point are walked downwards, so a data label or a tracker laid over the series passes through to the mark. So does an HTML label the chart draws over its drawing (Highcharts' `useHTML`, in its container).
- **Point or bar:** this is told by the series' shape, never by proportions. Highcharts says it in its series' class (`highcharts-bar-series`, `-column-series` and their kin are bars). Otherwise a `rect` is a bar, a `circle` or `ellipse` a point, and a `path` or `polygon` a bar when it shares an edge with a shape beside it.
- **Per drag:** what is found about a drawing (its labels and axes) and about each mark is kept for one drag and forgotten on the drop, at the drag's end, or after 700 ms without a `dragover`. Without that last case, a drag that ends elsewhere (Esc, or a release outside the page) would send this page neither `drop` nor `dragend`.
- **The outline:** CSS draws no outline on an SVG shape, so the outline is a box over the mark's bounds. The box is drawn in a closed shadow root of the extension's own host (`data-apc-outline`, no pointer events), as the pin and the cards are. It goes after the same 700 ms idle.

The reading's element is `path` (or the shape's tag) with the role `chart point` or `chart bar`, under the chart's heading as before. Its text is what the person sees at the mark (`describeMark` in `chart.ts`), its parts joined by " · ":
- **series:** the legend item of its series (Highcharts `highcharts-series-N`). In a chart of one series it is the chart's title ("SMU" above the plot), or, with markup that says nothing, the single label above the axes that is not a number. It is left out when it is the heading already.
- **category:** the category-axis label in line with the mark (under it for a vertical or line chart, beside it for horizontal bars), within half the space between two labels.
- **value:** exact only when it is visible text that belongs to the mark. That is either its own accessible text (`aria-label`, `<title>`, `<desc>`) or a data label of its series: on a point, above or below it; on a bar, on it or within 24 px past its end. Otherwise the value is read from the mark's place on the value axis by the straight line through the ticks, and only when that can be trusted: three ticks or more on one line, or exactly two when one of them is zero, which a log axis cannot show. The place is a point's centre, or a bar's end away from its baseline. The baseline is the edge the bar shares with the other bars of its series, else the axis's zero. The value is written as the axis writes its numbers (the unit shared by its non-zero ticks, so a bare "0" tick keeps the "%"), rounded to a hundredth of its step, as "≈ 930M (approximate, read from the chart's position)". When the geometry cannot be trusted, there is no value.
- **tooltips:** a tooltip is never the value. An HTML5 drag does not move the chart's hover, so a tooltip on screen is about the last point hovered, not the one dropped on.

**Labels and numbers.** Every label the reading uses passes the rule `readable` keeps text by: rendered, opacity, transparent ink, `clip-path` and `clip`, the overflow boxes around it, and an SVG clip path such as the plot's. `readable` now also honours an SVG clip path holding one rect. The HTML labels come only from Highcharts' own label groups (`.highcharts-data-labels`, `.highcharts-axis-labels`, `.highcharts-legend`).

The axes are found by their place, so a chart without classes works too: a column of numbers is a vertical value axis, a row of them a horizontal one, and the longest line of labels across the other way is the category axis. Highcharts' axis labels are told apart from data labels, the legend and the title by their classes. Numbers are read as charts write them (`parseNumber`):
- a suffix scales (k, M, MM, G, B, T), and % stays a percentage; a currency sign before is kept;
- when both "." and "," show, the last is the decimal; one that shows more than once groups thousands;
- one that shows once is a decimal unless exactly three digits follow it ("1.000" is a thousand, "98,51%" and "1,5" decimals);
- whatever groups thousands (a space, also no-break and thin, ".", "," or "'") must group them: one to three digits, then groups of exactly three, with one separator throughout. So "1 000M" and "1.000.000" are numbers, and "1.2.3" is none;
- the chart's decimal separator (`decimalOf`) is told only from labels that are numbers themselves among ticks and data labels, never from a title or a legend ("Crecimiento 1.5%").

A part that cannot be told is left out, never guessed. A mark whose category and value the chart tells neither of is not a target of its own: the drop reads as any other. If the mark can no longer be described at the drop, no element is sent and the dock says the page.

So on Datamind's "Venta neta", a drop on SMU's September point reads `Pointed at (path, chart point): SMU · S · ≈ 930M (approximate, read from the chart's position)`. On "Instock promedio", a drop on the SMU bar reads `SMU · 87,67%`.

Only the mark and the chart's own labels are read, nothing outside the chart, and consent is unchanged. A drop on the chart's background, a gridline, an axis, a plot band or the title reads the whole chart as before.

A label drawn twice is read once: a halo copy under it so it reads on any background, either Highcharts' `highcharts-text-outline` or a text or tspan drawn with a stroke only beside an unstroked twin with the same words at the same place (`isOutlineCopy`). A filled label is never dropped. Each SVG `<text>` is a word of its own, so labels no longer run together ("98,51%98,51%" before). The cost is that one token drawn as two `<text>` nodes reads apart ("100 %").

`apps/extension/test/chart.test.ts` covers a Highcharts-like line chart, an Instock-like bar chart, a chart with no classes and each review finding. `scripts/extension-e2e.mjs` step 12 drops on them in Chrome, including a plot band, a stale tooltip, an HTML data label over a point and a label hidden by the plot's clip path.

Everything the person can see in it goes, and only that. Its **text** is walked (`readable`), not taken from `innerText`, which gives text nobody can see: text under an effective opacity of 0.1 (`opacity` or `filter: opacity()`, the element's and its ancestors'), in a transparent colour, clipped away (`clip`, `clip-path`), outside the outlined element's box, or cut off by a box around it that clips what overflows it (`overflow` other than `visible`) is left out; a text node only partly cut off (a paragraph wrapped past a 20 px overflow box) gives only the words whose boxes show. The heading above it is read the same way. And **every visible control in it**, by the same rules and only when its box shows inside the outlined box cut to every clipping box around it (`showsIn`, `inOutline`): each with its accessible label: what was typed in each field, the chosen radio of each group (under the group's `legend` or label; a radio under the pointer says when it is not the chosen one), every checkbox, checked or not, and a `select`'s chosen options, native or ARIA (`role=radio`, `checkbox`, `switch` with `aria-checked`). The control right under the pointer comes first, marked `(pointed at)`. The extension's own cards and pins are never what a drop lands on.

TIN-571 first read only the choices of the pointed control's group and the typed value of the one field dropped on, with a 25-control cap on a form. On a Google Form the pin landed on the "Email" question's card, not its text box, so the typed email did not go. Tomas's point: the outline painted over what the person points at already tells them what goes, so the gesture is the consent, and the person decides about sensitive numbers (below).

The accessible label is `aria-labelledby` (resolved in the control's own root, so a shadow root's labels count), `aria-label`, its `label`s without the text of controls inside them, or `title`; a typed field falls back to its `placeholder` or name. A control the person cannot see is never read: not rendered, nearly transparent (an effective opacity, its own times its ancestors', under 0.1), of no size or 1 px, off the page, clipped away (`clip`, `clip-path`) or `aria-hidden`, and for a field one types in, text in a transparent colour (`visuallyHidden`, `controlVisible`). Only a native radio or checkbox counts as seen through a label the person sees, since custom widgets hide that input under a styled label; a `select`, a field one types in and anything with a `role` must be seen themselves. A control the person cannot see (a near-transparent field laid over the page as bait, or one reached through a visible label) is not read at all, not even its label. A hidden input is never a control. A field in an open shadow root is found under the pointer through its host, and counts in the outline of its host.

What the filters below find is of two kinds, by filters the extension and the hub share (`shapeFields`, `textSecret`, `namesSecret`, `namesCredential` and `redactNumbers` in `apps/dock/src/worker/reading.ts`; `classify` in `read.ts`, which also sees the markup):

- **A password or a code never goes, in any mode**: `type=password`, an `autocomplete` of `current-password`, `new-password`, `one-time-code`, `one-time-password` or `cc-csc`, a name, id, label or placeholder that names a password (pass, pwd, contraseña, senha, clave), a PIN, a one-time code (otp, totp, mfa, 2fa) or a card's security code (cvv, cvc, cid, ccv, "security code"), or a short number under "code"/"código" (`codeSecret`). The content script never puts its value in a reading: it says `(left out: password or code)`, and flags the field `credential: true`. The hub turns any field so flagged, or whose label or value says so, into the same words, even when marked as chosen; an older extension sends no flag, and its labels decide.

  What these checks read is the page's own markup at the moment of the drop. A page that rewrites its own password field before the drop (its `type`, `autocomplete`, name and label, with `-webkit-text-security` to keep the dots) gets its value read as an ordinary field. That is outside what the filter protects against (13.5): the page already holds what is typed in its own fields and can send it anywhere itself; the filter protects the person against accidents on ordinary pages, not against the page.
- **A sensitive number (a card, an account, a national id) goes as the person chose.** One setting for every site, in the popup and on the welcome page (`sensitive` in `chrome.storage.local`, read at each drop): **Ask per drop** (the default) leaves them out, and when it did, a card after the drop says "Sent to your agent. N sensitive values left out." with **Include them this time**, which sends that drop's reading again with them. Each drop's reading gets an id in the page when it is taken; the service worker keeps that exact reading by its id in `chrome.storage.session` (memory only, 10 at most, 2 minutes each), marks it usable once that drop's consent is given, and the card and its `include` message carry only the id: the service worker sends the reading it kept, once, to that drop's dock and agent, and refuses it under any other setting or before that drop's consent. A later drop never takes its place (a first version sent whichever drop the page had last, so Include after a drop held for the dock's Allow could send a later drop still waiting on its own card; found by review); **Send if it's in the outline** sends them with no question; **Always leave out** is the behaviour of TIN-571, with no button. The consent card says, by the setting, what will happen to them. The extension marks every value it sends by the person's choice `sensitive: "included"` (a field; the outlined text, `element.sensitive`; the selection and its block, `selection_sensitive`), and the hub keeps a sensitive value only with that mark: an old or wrong extension's unmarked one is still withheld. `page_text` says `(sensitive: the person chose to send it)` after such a field.

A sensitive value left out says `(left out as sensitive)` in a typed field, is counted for a choice ("N fields left out as sensitive"), and in visible text is replaced by `[sensitive number left out]`. What the filters look at, whatever the field is called:

- a field's label or value that holds what looks like a secret number. First the text is normalized (`secretForm`): compatibility forms folded (NFKC: fullwidth and mathematical letters and digits), every decimal digit of any script as 0 to 9 (Arabic-Indic, Devanagari…), format and zero-width characters removed, every dash or minus as "-". Then it is held back when, with everything but letters and digits removed, it has a run of 8 or more digits (a card, an account, an id, a phone number, a date written as digits); when it has 12 or more digits in all, whatever separates them, letters included; when it holds an IBAN of its country's length with valid check digits, in any case; or a RUT or RUN: its groups split by dots, spaces or nothing, any dash, and a check character that may be a Greek or Cyrillic look-alike of K (`12.345.678-5`, `1 234 567–K`, `1.234.567-К`), or a value ending in a dash and a check character with 7 to 9 digits before it, whatever separates them (`12.345x678-5`);
- a short number (3 to 8 digits) in a field named only "code" or "código" (a one-time code, a card's code), but not a postal, zip, promo, discount, coupon, country, area, product or tracking code (`codeSecret`);
- a field whose markup says so: `type=password`, an `autocomplete` of `current-password`, `new-password`, `one-time-code`, `one-time-password` or any `cc-*`, or a name, id, label or placeholder that names a card number or code (cvv, cvc, cid, ccv, pan), an account (account, acct, iban, clabe, routing number, "Nro. de cuenta"), a national id (ssn, sin, rut, run, dni, cédula, nif, curp and others), a password (pass, pwd, contraseña, senha) or a one-time code (otp, totp, mfa, 2fa), as whole words or joined (`cardNumber`, `numero_de_tarjeta`). SIN and PAN count in a label only in capitals, since "sin" is Spanish for "without" ("Envío sin costo") and "pan" for bread.

The hub runs the same filters again on every label and value it receives (it cannot see `type`, `autocomplete` or a name, so the extension applies those, and marks a value it found sensitive by its markup alone, which the hub then withholds unless it is also marked as chosen). Caps: 20 fields, 100 characters per label and 200 per value, 1,500 in all; the rest are counted in "N more fields not included". The state is read only on the drop or when the person moves the pin (`readAt` in `content.ts`), never while they fill the form, and it goes in `page_text` after what was pointed at, as untrusted as the rest. **Sensitive numbers in visible text (TIN-617, TIN-619).** Under Ask per drop and Always leave out, the outlined text (its words, name, heading, column and row), the selection and the selection's block are searched for sensitive numbers, and only each number is replaced by `[sensitive number left out]` (`redactNumbers`), the rest of the text kept. A selection that was nothing but such a number is sent as "(selection left out as sensitive)", without its context. Visible text holds many figures, so a number is found by what it is, with validators, not by counting digits:

- a payment card, by one grammar of how a card number is written (TIN-762): one unbroken run of digits (or one written digit by digit, "4 1 1 1 …"), or groups of at least 4 digits of which only the last may be shorter (4-4-4-4, 4-6-5, 4-6-4, 4-4-4-4-3); joined by spaces, commas, dots, slashes, dashes, up to 6 other characters, or up to 16 letters with no space (letters a page put inside a number: "Pay 4111aaaaaaaa1111aaaaaaaa1111aaaaaaaa1111 today", "4111 then 1111 then 1111 then 1111"), but never by a percent, per-mille or currency sign; whose digits make 13 to 19 that start as the card networks' numbers do (4, 5, 6, 3, or 2221 to 2720) and pass the Luhn check;
- an IBAN with valid check digits, written in groups ("GB82 WEST 1234…") or with letters between its digits;
- a RUN or RUT with its dash and a valid modulo-11 check character (`12.345.678-5`, `1.000.005-K`).

So a list of years ("2019 2020 2021 2022"), dates ("from 2020-01-01 2020-12-31", "2026-11-04"), scores, phone numbers ("1234 5678"), a run of percentages ("98,51% 96,23% 90,42%", spaced or not) and of amounts ("$293.460.353 $332.718.794") stay: a figure's digits come in groups of 1 to 3, where no card starts and after which none goes on, so a figure next to a card does not swallow part of it either. All digits are folded first, as in `secretForm`, and the span replaced is the one in the text as the person sees it. The stricter rules above (8 digits in a run, 12 in all) stay for a field's value, which holds one value. Under Send if it's in the outline, visible text goes as shown.

TIN-571 sent the outlined text as shown and held the selection's whole block when it had 12 digits within any 24 characters. The first TIN-619 rule counted 12 digits in a run of number-like words: a review (Grok, on PR #132) found card numbers it let through ("4111, 1111, 1111, 1111", groups between short words) and figures it swallowed (a list of years, two dates, a row of scores), and a selected date withheld whole. Hence the validators. The validators still took a run of chart labels for a card: a whole-chart reading of Datamind's "Instock promedio" (TIN-760) came out "98,[sensitive number left out],81%", as the Luhn check passes one window of digits in ten. TIN-762 made the card a grammar of how one is written (groups of at least 4 digits, no percent or currency sign between them) rather than a list of separators, keeping every form the reviews found.

A first version read every typed value in the form around the drop, with a blocklist of field names and a narrow value check. A review (Grok, on PR #130) found it sent a lowercase IBAN, a card number grouped with dots or slashes, a RUN, an account number under "Nro. de cuenta", a card number that was a checkbox's label, a field labelled from a shadow root, transparent bait fields and every control of a page-sized `role=group`. So the scope became the choices and the one field dropped on, and the filters look at what a value is, not only at what the field is called. A second review found the same numbers written with other characters (an en dash or a minus in a RUN, a zero-width space, fullwidth, mathematical or Arabic-Indic digits, letters between the digits), a covering field at opacity 0.02, a hidden `select` or `role` field read through a visible label, and hidden inputs counted toward the 25: hence the normalization, the 12-digit rule and the stricter visibility.

Images and formulas give their alternative text in place, not what renders (TIN-422). An image gives its `alt`, or says `[image with no alt text]` so the agent knows something is missing; `alt=""` marks decoration and gives nothing. A formula gives its `alttext`, `aria-label` or TeX annotation (the spike read MathML as "𝐿 𝑇 ∗ 100"), and an `svg` its `aria-label` or `title`. Without any of these in the block, the text is simply `innerText`; with them the content script walks what is rendered, since a page often keeps a hidden copy of a formula beside the one it shows. Wikipedia clips its MathML out of sight beside an image of the formula with the same text, which counts as rendered, so the same alternative text twice with no words between reads once (found on the real site, not on a test page). A drop on a formula or a drawing takes it whole, not the glyph under the pointer, and a drop on an image with alternative text reads that image when no block of text holds it. Only a real `th` counts as a column header, since the first row of a plain table may well be data, and an ARIA grid built of divs is read as any other box of text. The selection is still the browser's own text, so a selected formula comes as its glyphs.

A drop that is outlined nowhere (a margin of the page) reads only the title and address and any selection. Never in a reading: passwords and codes, what the person cannot see, anything outside the outline, sensitive numbers the person did not choose to send, hidden inputs, cookies or storage, other tabs, or a screenshot. Until TIN-571 no form value went into a reading. This is the extension's reading of pages without APC: an APC app (Pulse, Signals, any app that speaks APC) decides itself what it exposes to an agent, through its own tools. Text the person selected inside a field goes along as the selection; a password field gives only dots.

On the wire, the extension is one more app of the hub, with id `page` and name "This browser". The hub exposes `page__get_reading`. The focus has kind `page_reading`, with `app: { id: "page", name: "This browser", origin }` (the page's origin) and `next: "page__get_reading"`. A reading lives at the hub until the next drop replaces it or it is 10 minutes old, so the agent can read it again while it answers; reading it marks the focus seen. The end is enforced: a Durable Object has one alarm, so it rings for whatever comes first, the oldest reading or the dock's end, and a reading that ends takes the agent's focus on it too, since the focus holds the page's address. Until TIN-422 a reading ended only when something next looked at the readers, so in a dock nobody used it could stay until the dock expired, up to 7 days later. "Kept" means in the live database: Cloudflare's point-in-time recovery can restore a SQLite Durable Object up to 30 days back, so deleted text stays recoverable there by whoever controls the account (the README says so). The hub never calls that API.

### 13.3 Consent

A drop is always the gesture: nothing leaves a page unless the person drops their agent on it. What the extension asks on top of that changed after the first real use (TIN-465). A grant per site made the list long fast, and it hid in the collapsed popup. Worse, a drop on a site without a grant could not be noticed at all: without host access the extension has nothing on the page, so the person only saw the not-allowed cursor.

- **A site comes with its frames (TIN-752).** Allowing a site from the popup asks, in the same Chrome prompt, for the origins of the tab's frames too, by their real origins after redirects (`chrome.webNavigation.getAllFrames`, `siteGrant`), so a page whose content is a frame from another origin takes the agent there as well. On a site already allowed whose frames are not, the popup says which origins they come from and offers to allow the site again with them. `webNavigation` is a required permission, not an optional one: the frames' origins must be known before the prompt, and a second prompt after the first would need a second click. Chrome shows it at install as "Read your browsing history"; the extension only lists the frames of the tab the popup is open on, or of the tab the agent is dragged over, and keeps nothing.
- **One browser grant, once.** On install the extension opens a welcome page that explains it and asks for access to any page (`https://*/*`, `http://*/*`, still `optional_host_permissions`, so it can be refused or revoked). With it, the content script is on every page and notices every drop. A person who refuses can still grant one site at a time from the popup, as in TIN-421.
- **Consent per site, in the page, on the first drop.** The extension keeps its own choices per site, not Chrome. On a site with no choice yet, the drop shows a card where it landed: "Send this to your agent? Everything you can see inside the outline goes along, including what you typed there. Sensitive numbers (card, account, id) go only as your setting in the APC extension says; passwords and codes never. It passes through the APC hub of your dock, on Cloudflare (kept 10 minutes at most), and then to your agent's provider. **Just this once** · **Always on this site** · **Not here**", with what will happen to the outline's sensitive numbers when it holds some (TIN-619). Just this once sends and asks again next time. Always sends now and later. Not here sends nothing now or later, and says so on each drop. A site granted by itself from the popup counts as Always, since the person picked it. The popup lists the Always and Not here sites, each with Remove.
- **Sensitive sites always ask.** On a sensitive site the card offers only **Send** and **Not now**, never Always. A site is sensitive by its domain alone: a government domain (a `gov`, `gob` or `mil` label, as in `sii.gob.cl` or `gov.uk`) or the restricted `.bank` and `.insurance` TLDs, which only verified institutions can register. Nothing is guessed from a site's name (TIN-478): the first rule did, with a few mail hosts and words like "bank" or "salud", and missed most real banks and payment sites (santander.cl, bci.cl, paypal.com, sii.cl…); no list could keep that promise, so the extension makes none. Instead the person sets any site to **Always ask** from the popup, and removes it from the popup's list.
- **"Never ask", opt-in.** Off by default, switched on in the welcome page or the popup after a warning that says what it means: every drop is sent at once, on any site, sensitive ones included, except a site set to Not here (since TIN-571). It removes the questions, not the drop.
- **The card says what goes along from a form (TIN-571).** Every card adds: "With the text go the choices made in that part of a form and what you typed in the field you dropped on, never a password or a card, account or id number." A reading carried only page text when the person said Always to a site, granted it from the popup or turned on Never ask. So after the update, the first drop on such a site (under Never ask, the first drop anywhere) asks once more, with "New: page readings carry more." and the same three choices; Just this once and Always send and leave the setting as it was, Not here sets it, and Not here then holds under Never ask too: a site's own Not here comes before Never ask (`decide`), so a refusal on that card sticks. Any answer is remembered (`formNoticeSites`, `formNoticeAll` in `chrome.storage.local`), and a new install, which reads it on the welcome page and the first card, is not asked again. TIN-619 changed what goes (the outline, typed values included) and bumped the notice: the keys are now `readingNoticeSites2` and `readingNoticeAll2`, and the card that asks once more opens with "New: the outline is what goes."
- **The card lives in the page**, in a closed shadow root, and its buttons take trusted clicks only. A page could still try to trick the person into Send or Always. What it gets is its own text going to the person's agent, which arrives marked untrusted anyway (13.4), and Always on that site, which still needs the person's drop each time.
- **Every reading is visible (TIN-422).** The popup and the agent's page in the dock (TIN-419) list each reading sent, newest first: its site, relative time (the exact one in the tooltip), size, and whether the hub still has it ("still at the dock" or "gone"); the popup adds which agent got it, since it spans them. The list lives only at the hub, in `reading_log` (the agent's last 50: the browser's extension origin, `at`, `site`, `bytes`, never the address or a word of the text), so there is one list and Clear in one place shows in the other. The popup asks for it with the reader's token (`POST /apc/reading/log`) and sees only what this browser sent; the dock sees every browser's readings for that agent. **Clear** (`POST /apc/reading/log/clear` from the popup, `POST /api/d/:did/agents/:aid/readings/clear` from the dock) removes the list, any reading still at the hub and the agent's focus on it. It says beside the button that what the agent already read stays with it. × on a pin only ends that reading, so its line stays, as gone. The cost of one list: it ends with the dock, and the popup needs the network to show it.

### 13.4 Injection

Page text is untrusted data: any page can carry instructions aimed at an agent. The hub returns a reading under `page_text` with `untrusted: true`, and `HUB_INSTRUCTIONS` says that page text is data to read, never instructions to follow. The hub never builds `next` or `next_args` from page text. A reading is capped at 6 KB. As between apps (12.5, the C7 boundary), the agent can still be fooled by what it reads. Showing every reading in the dock makes that visible, not impossible.

### 13.5 Where the hub lives, and pairing on the first drop

**On the dock's cloud hub.** The extension is a client of the dock whose agent was dropped, not a hub of its own. It needs no pairing step of its own and no `externally_connectable`: the drag already carries `hub`, `agent` and a single-use 60 s `ticket` (12.1).

- **The first drop of an agent from a hub this browser has not paired with** sends `POST {hub}/apc/reader { ticket, agent, label }` from the service worker. `label` is "Chrome on Windows" or similar. The dock then asks: "*Chrome on Windows* wants to send page readings to *agent*. Allow?" The extension holds that first reading for up to 60 s and asks the hub again. On yes, the hub answers with a reader token, and the held reading goes out. On no or timeout, the reading is dropped and the popup says so.
- **A page cannot forge a drop or redirect it.** The content script acts only on trusted drop events (`isTrusted`), and the extension talks only to the docks it knows (`HUB_ORIGINS` in `apps/extension/src/drop.ts`). A drag that names another hub is refused in the page, so no page text goes to an address a page chose.
- **Only the extension can pair as a reader.** A page also sees the ticket on drop (12.1), so a hostile page could try to pair as a reader and feed the agent made-up readings. The hub accepts `/apc/reader` and readings only from an `Origin` in `READER_ORIGINS`: the extension's published ids (`chrome-extension://<id>`, one per store). A page cannot forge that header. This is the same rule as `HUB_ORIGINS` and `APP_ORIGINS`.
- **Later drops** push the reading with the token for that hub (`chrome.storage.local`, one per hub), with no channel held open. A drop from another browser's dock pairs with that dock, after the person allows it there.
- **Unpairing** happens in the dock (the agent's page lists "This browser" as an app, with Unpair, as in TIN-410) or in the popup. Either side drops the token.

**The cost:** the text of real pages now passes through Cloudflare, and then to the agent's provider. Until now only Pulse's synthetic data did. Since TIN-619 that is everything the person can see in the outline, what they typed there included (13.2), read once on the drop; passwords and one-time codes are held back in the page and again at the hub, and card, account and id numbers go only as the person set (Ask per drop by default), in fields, in the outlined text and in the selection, with the hub withholding any not marked as chosen. The threat these filters answer is a normal page sending something the person did not see or did not consent to: text and fields outside the outline or hidden in it, a reading other than the one they dropped on, a number they did not choose to send. A hostile page is not in it as far as its own content goes: it already holds what is typed in its own fields and can send it anywhere itself, so a page that rewrites its own fields to get past the filters (13.2) gains nothing it did not have. So the per-site consent card and every Allow in the dock and Float say so (`READER_NOTICE`: what a reading carries and where it goes), the README adds readings (their content kept at most 10 minutes; the log keeps site, time and size), and the hub never logs a reading's text: `apps/dock/test/hub-readings.test.ts` runs `hub.ts` itself on Node's SQLite, sends a reading through it and searches every table and the console for its words.

**Presence.** The extension reports no presence: on pages without APC there is no `then` or `page_open`, so nobody learns which sites the person visits. A new reading reaches the agent as `attention` on its next hub call, as an unread pin does.

**A local hub** (native messaging to a process on the person's machine) is not built. It would come only if keeping page text on the person's machine turns out to matter to them, and would need a desktop component like Pulse for desktop (TIN-396).

### 13.6 Dock, Float and the extension

**The pin (TIN-469).** Once a reading is sent, the agent's mark stays pinned where it was dropped, as a pinned agent's icon stays on its target in an APC app (TIN-355). It sits in the left margin at the paragraph's first line; with no room there, past its right edge, or inside its top right corner as Pulse places a badge on a row, so it never covers the first words; and it follows the paragraph through layout changes. It looks like Pulse's pin badge (`pin-badges.tsx`): a rounded square with a dashed, breathing outline until the agent reads the reading, then a green check, and × in its corner. It shows the agent's logo (the PNG badge the dock drew, TIN-388, which `/apc/reading` now returns with the agent's name) and the agent's name as its tooltip. Its ring says what the agent did, as the agent bar does (TIN-394): accent while the agent has not read the reading, green once it called `page__get_reading` (the hub records `read_at`), grey once a newer drop elsewhere replaced the reading at the dock. A page has one pin per agent, so a new drop moves it. Dragging the pin by its mark to another paragraph of the page moves the agent's focus there (TIN-471), as dragging a pin's badge does in Pulse (TIN-354): the extension reads that paragraph and sends it with the browser's reader token, with no ticket, no dock Allow and no consent card, since the person consented when they dropped the agent on that page. Esc, or a drop off any paragraph, puts it back. Finding the paragraph under a point skips the extension's own pins, which otherwise hid the paragraph under a pin just released. **×** clears the reading and the agent's focus at the dock (`POST /apc/reading/clear`). The content script asks for the state (`POST /apc/reading/state`) every 3 s until the reading is read, then every 10 s until it is replaced, so a read pin still turns grey (first built to stop once read, which left read pins green; found against production). A reload or a navigation drops the pin: finding the same paragraph again is unreliable on pages that change.

**Opening the dock and Float from the extension (TIN-473).** The popup has **Open dock** and **Float**, also as shortcuts (Alt+Shift+A, Alt+Shift+F, changeable at `chrome://extensions/shortcuts`). Open dock brings the dock to the front if a tab or window has it, found by the start of its address (a match pattern takes no port, and a local dock has one), or opens it in a narrow window like the installed app's strip. The dock is the one this browser sends readings to, or apc.tineira.com. Chrome opens Document Picture-in-Picture only from a click in the dock's own page, so Float opens the dock with `?float=1`, where a prompt takes that one click and stays until Float opens; ✕ or Esc dismisses it.

The dock window and Float stay the only places an agent is dragged from, in every browser. The extension adds no UI to drag from. It only makes pages take the drop and keeps its settings in the toolbar popup. Without the extension, everything in section 12 works as before; drops on pages without APC simply do nothing.

## 14. The core, a conformance suite, and revoke from the app (TIN-577)

**The core.** The APC standard (0.2.0, `packages/protocol/CHANGELOG.md`) names what every APC app implements, per grant, whichever way agents reach it: the view, the pin, presence, the focus format, `get_current_view` and `wait_for_focus`, and revoke from the app (`packages/protocol/src/core.ts`, summed up in `packages/protocol/README.md`). A dock's hub is one more holder of a grant, so the core is the same for it. What is not core belongs to a profile, and an app offers one or both:

| Profile | The agent connects to | The profile's own parts |
|---|---|---|
| Direct | the app's own MCP URL, one per agent | the grant per agent, its secret URL, the list where the person makes and names agents |
| Dock | a hub, once | receiving the drop (handle and ticket), consent in the app, `/apc/pair`, `/apc/confirm` on every drop, `/apc/revoke` from the hub |

Pulse implements both (its deploy, with `APC_V2=1`, runs Dock only) and Signals Dock. Where they differed, the code now agrees, or the contract says what may differ:

- Signals publishes presence after each successful call, as Pulse does (`get_post` names its post); its page receives it and does not draw it yet.
- Neither sends `then` on a `wait_for_focus` that came back with no focus: that result ends the loop. Signals used to send it while its page was open.
- An app without a view-sharing switch (Signals) always shares, so it always reports `page_open`; Pulse leaves it out while the person does not share their view.
- An unknown or expired grant answers 404, whatever the body says (`unknown_grant`, `sandbox_expired`, `expired`).

**The conformance suite.** `@tineira/apc-conformance` (`packages/conformance`) checks an app against the core the way an agent or a hub reaches it: JSON-RPC over the app's MCP endpoint, stateless. What only the app's page knows (whether a page is open, the view it reports, the pin the person drops, the presence the app sends it, Revoke) comes through a small adapter the app writes. It checks: the two core tools and their arguments; the view as identifiers and no focus before a pin; a pin riding as `attention`, in the structured result and the text, until it is read, with `next` and `next_args` that read it, and a new pin replacing it; `wait_for_focus` returning a pin dropped during the wait, timing out cleanly, and ending as soon as the page is closed; `then` only while a page is open; presence with ids only, naming the target a read touched; and revoke (below). It is framework-free: `apcConformance(app)` gives named checks for any test runner, `runConformance(app)` a report. `@tineira/apc-conformance/workers` runs a Durable Object on Node's SQLite with fake pages, so `pnpm test` runs the suite against Pulse (Direct and Dock) and Signals with no network (`apps/demo/test/conformance.test.ts`, `apps/signals/test/conformance.test.ts`), and checks that the suite fails an app whose Revoke does nothing.

**Revoke from the app.** The person must always be able to cut an agent from the app itself, whichever way it came. Before, a dock agent could only be cut from the dock, which called the app's `/apc/revoke`; with the dock closed, expired or down, the app kept serving it. Now every agent in `<apc-agents>` has Revoke: ⊘, then **Revoke?** within four seconds (event `apc-revoke`), which Pulse and Signals send to their own server (`POST /api/s/:sid/grants/:id/revoke`, owner only).

- **At once, in the app alone.** The sandbox (or Signals' feed) deletes the grant, its pin and, for a dock agent, its dock link, in synchronous storage work after one hash, and records the revocation: the grant's id, a SHA-256 of its secret (the secret itself is not kept), the dock it came from and the time. It calls nobody, so it holds with the hub down.
- **The URL answers revoked.** From then on every request to the grant's MCP URL, whatever the method (the revoked check comes before the 405 for a GET or a DELETE, and the suite checks both), gets HTTP 403 with `{ error: "revoked", revoked_by, revoked_at, message }`, `revoked_by` being the app's host (`revokedResponse` in `@tineira/apc-server`). An unknown grant still gets 404, so a holder can tell "taken back" from "gone". The record lives as long as the sandbox; once the sandbox is gone the URL answers 404, and never works again either way.
- **Calls already running end revoked.** Every tool runs inside the app's wrapper, which checks the grant before the tool and again after it: a call that started before the revoke (the next poll of a wait, or another call in the same request) returns the revoked answer as a tool error, with no attention, no `then` and no data. A `wait_for_focus` in flight sees its grant gone at its next poll (2 s) and ends. The check is by the grant's own secret (is a grant with this secret still there?) and the revocation by the secret's hash, both taken when the request came in, never by the grant's id (TIN-606): ids are 32 bits, and a later grant may take a revoked one's, which would keep a revoked call running under the new grant, or answer `revoked` for a later grant that was only given back.
- **The hub learns it on its next call.** The hub reads the app's error body (`AppCallError.code`): on 403 `revoked`, or a running call's revoked answer, it marks the pairing `revoked`, stops relaying to it, and drops what it kept from the app (its last view, its tools, the pin it took, `page_open`). The dock shows the line as **Revoked by** the app's host, on the agent's page (with **Remove**, which only removes the line) and on its tile. A relayed call to that app gets `revoked` with the same words. `/apc/confirm` never confirms a revoked pairing.
- **It never comes back by itself.** The app dropped its dock link, so the agent's next drop there goes to consent in the app, then in the dock, and makes a new grant with a new URL; the new pairing replaces the revoked line and keeps the app's id. A Direct agent needs a new URL.
- **Consent in the app is the app's server's to check** (APC 0.7, TIN-606). The page used to decide from the links it last loaded: a page that missed the revoke (its socket down, a laptop waking) sent the next drop as a pin, and the server, finding no link, made a new grant with no one asked. Now every dock drop goes to the server, whatever the page shows. For an agent it holds no grant for (never paired, revoked, or one the dock no longer confirms), Pulse and Signals answer `consent_required` with a nonce (`DockConsent` in `@tineira/apc-server`: 128 random bits, kept in the sandbox's own storage, two minutes, once, for that dock and agent). The page shows its consent with it, and only the Allow that sends it back makes a grant and calls the dock's `/apc/pair`. The drag's ticket is not spent meanwhile. One drop of an agent is answered at a time (Grok on #123): a second request for the same dock and agent while the first waits on the hub (a double-clicked Allow) answers `pairing_in_progress` and changes nothing, and both apps link the new grant to the agent only once the hub took it (Pulse's `hub_links`, Signals' grant `agent`), so no drop can find it half-made, confirm it with a hub that has not stored it yet, and revoke it. The consent's buttons turn off on the first answer.
- **Re-paired before the hub heard** (TIN-606). A drop after a revoke in the app, before any call told the hub, used to leave the old line as `paired`, so the new pairing got the id `pulse2` and the old one later turned **Revoked by** and stayed. Now, when an agent asks to pair again with an app it holds a paired line for, under another MCP URL, `pair()` asks that line (the quick look, alongside reading the app's `apc.json`): revoked, it is marked and then replaced, the new pairing keeping the app's id; gone (404), it goes. A line that still answers is a live pairing of the same app (a second sandbox of the person's), and stays beside the new one.

Every path to the app's data after a revoke, and what closes it:

| Path | Closed by |
|---|---|
| A new request to the grant's MCP URL (the agent, the hub, anyone who copied the URL) | the grant is gone; the URL answers 403 `revoked` before any tool runs |
| A call already running, or another call in the same request | the wrapper's check before and after each tool; a wait ends at its next poll |
| Pinning the revoked grant from the page | `pin` needs the grant; it answers `unknown_grant` |
| The dock re-confirming on a drop (`/apc/confirm`) | the app holds no link for that agent any more, so it asks the person instead; the hub refuses a revoked pairing anyway |
| What the hub kept (the last view, the pin it took, tools) | identifiers the app gave before the revoke; the hub drops them on its first call to the app after it. `get_current_view`, `call_app_tool` and `list_app_tools` call the apps first, and `wait_for_focus` asks the app of an unread pin before it hands the pin over, so none of them hands over what a revoked app gave. That look at the pin's app alone is bounded by `LIMITS.pinLookMs` (2 s) or the wait's own timeout, whichever is shorter (TIN-606; it used to ask every app for up to 6 s): an app that does not answer in time keeps its pin, as below. A call that reaches no app (an unknown tool, `page__get_reading`) can still carry such a pin as `attention` until the next of those: target ids from before the revoke, never app data |
| Pairing again | a new drop, consent in the app (checked by its server: the nonce) and in the dock, a new grant |
| A page that missed the revoke, sending the drop as a pin | the server finds no link and answers `consent_required`; no grant without the nonce |

**An app that revoked and cannot be reached.** The hub learns a revocation only from the app's answer. While a revoked app is down or unreachable, the hub gets no answer, so it keeps the pairing as paired: its last view and the pin it took (target ids), and its tools still listed as `<app>__<tool>`. Those ids came from the app before the revoke, and any call that reaches the app is refused (403 `revoked`); one that cannot reach it fails as unreachable. The line turns to **Revoked by** on the first answer the hub gets. The same holds for an app slower than `LIMITS.pinLookMs` when a wait hands over its pin.

`apps/dock/test/revoke-from-app.test.ts` runs the real hub and the real Pulse sandbox in one process, each on Node's SQLite, with fetch routed between them: a paired dock agent is revoked in Pulse with the hub down (Pulse makes no call), its URL answers 403 `revoked` to every method with no data, the hub's next call marks the pairing revoked by `pulse.test` and leaves nothing of Pulse's in its tables, a wait running through the hub ends, the next drop asks again and pairs anew, and the hub never confirms the revoked pairing. Since TIN-606 it also checks that a drop sent as a pin by a page that missed the revoke reaches no dock and makes no grant until the consent's nonce comes back (and no other nonce does), that a drop the dock no longer confirms asks again with the same ticket, that a drop before the hub heard of the revoke replaces the line under the app's own id while a second live pairing of the same app stays beside it, and that a wait hands over an unread pin of a slow app after `LIMITS.pinLookMs`, asking only that app. `apps/demo/test/conformance.test.ts` and `apps/signals/test/conformance.test.ts` check that a running call is cut by its own grant when a later grant takes its id, both ways, and that no grant is made without the nonce; `packages/server/test/consent.test.ts` covers `DockConsent`.

Not covered by the suite: drawing presence (the page's own), the agent bar's two-click Revoke in a browser, and OAuth revocation, which replaces the secret URL later.

## 15. Apps the hub does not know (TIN-580)

**The idea.** The person may pair any APC app, after a warning in the dock (§ 18). The hub holds every app it does not know to a set of rules, so the warning only adds the person's informed yes to protections that already exist. (This section was written while only `APP_ORIGINS` could pair, behind an `OPEN_PAIRING` flag; § 18 replaced the flag with the person's approval and a kill switch.)

**Verified and unverified.** An app in `APP_ORIGINS` (or on localhost under vite dev) is **verified**: it pairs and works as in sections 12 and 14. Any other app is **unverified**: it pairs only once the person approves the warning (§ 18), and not at all while the kill switch `UNVERIFIED_PAIRING` is `closed`. The rules live in `apps/dock/src/worker/trust.ts` (pure, with its limits in `LIMITS`), the transport in `app-client.ts`, and their use in `hub.ts`. The pairing row records `verified` and the name the app declared; a row from before has no flag and counts as verified, since only `APP_ORIGINS` could pair then.

- **Identity is the domain.** An app names itself in `/apc/pair`, so any app could call itself "Pulse". An unverified app's id, and so its tool prefix, comes from its host and port (`evil.example` is `evil_example`, its tools `evil_example__<tool>`), at most 40 characters. A domain id always holds a `_` and never `__`, while a verified id is `[a-z0-9]` and the browser's is `page`, so the two kinds never meet. Another origin that maps to the same id (`a-b.example`, `a.b.example`) is refused rather than numbered, so no app answers under a prefix the agent has already seen. The dock and the agent see the host as the app's `name`; what the app calls itself is `declared_name`, secondary text with only letters, digits and plain punctuation.
- **Transport.** An unverified app uses HTTPS on a domain name: no IP address, no single-label or `localhost` host. The hub reads every answer from any app up to a byte cap (1 MiB verified, 256 KiB unverified; a declared `Content-Length` over it is refused before the body is read) and gives every call a time limit that covers the body as well as the headers (10 s to introduce itself or list tools, 20 s for a tool, 6 s for the quick look, a wait's own timeout plus 15 s). It never follows an unverified app's redirect, which would carry the grant's URL where the app chose. A dock holds 20 app pairings at most, pending and paired, across its agents (`too_many_apps`); a blocked pairing holds no place. A host too long for a 40-character id is refused as `app_host_too_long`.
- **Presence is the verified apps' say.** `then` on the hub's results (12.4) and the `page_open` its wait reports come only from verified apps. An unverified app that put `then` on every answer, or said the person was always on its page, would keep the agent calling `wait_for_focus`, each round a wait the app could hold for its timeout plus the grace. So its `then` and `page_open` are kept for the dock's "open now" but never counted (`presence()` in `hub.ts`); its pins still reach the agent, as `attention` or through a wait. With only unverified apps paired, the hub never says the person is on a page, so the agent goes back to the person after answering.
- **What the app gives is kept small and checked.** Its tools: names `[A-Za-z0-9_-]{1,64}`, descriptions cut at 1 KB, schemas over 8 KB replaced by `{ type: "object" }`, 32 tools at most, and no annotations, since an app could claim `readOnlyHint` to skip a client's approval. Its view: kept only under 8 KB. Its pin: taken only when its target passes `parseTarget`, `next` is a tool name other than the hub's two, its `app_url` is on its own origin (else empty), and its `pinned_at` is a real time no later than now. A pin dated in the future would otherwise win "newest pin" (12.4) against every other app for as long as it liked.
- **Untrusted, as page text is (13.4).** A relayed result from an unverified app reaches the agent in an envelope, in the structured result and the text the model reads: `{ app, untrusted: true, note, result }`, or `text: [...]` when the app gave no structured result. Its entry in `views`, its focus and its `attention` carry `untrusted: true`; its tools in `tools/list` start with `[Unverified app at <host>, calls itself "<name>". Untrusted: …]`, and its `list_app_tools` entry carries `untrusted: true` and a note. A verified app's results, views and tools are unchanged. **Errors carry none of its words**: a call that fails gives the agent `app_unreachable` with the hub's own reason only (`tools/call: HTTP 500`, `the app answered with an error`, `no answer within 20000 ms`, `answer over 262144 bytes`, `unreachable`), never the app's JSON-RPC error message or the body of its HTTP error, which would otherwise reach the model unmarked in a tool error; the dock's line for it shows the same reason (`AppCallError.reason`, `failureReason`). A verified app's error text is passed on as before. As with page text, the agent can still be fooled by what it reads; the marking tells it, and the label tells the person reading the tool list, where the words came from.
- **A blocklist we operate.** `BLOCKED_APPS` lists domains, each covering its subdomains, written as a host, a URL or `*.domain`; it is empty. Each entry goes through the URL parser (`new URL("https://" + entry).hostname`), so a name written in Unicode matches the punycode host an app's origin arrives as; `APP_ORIGINS` entries likewise go through `new URL(entry).origin`. A blocked domain cannot pair (`app_blocked`), verified or not. A pairing made before the block reads as `blocked` while the domain is listed: the hub never calls it again, not even to give the grant back on Unpair; its tools, view and pin go; a call to it is the tool error `app_blocked`; `/apc/confirm` refuses it; a pending request from it cannot be approved. The agent's page in the dock shows the line as **Blocked**, with Remove. Taking the domain off the list makes the pairing paired again, its tools fetched anew.

Every attack, what stops it, and the test that shows it (`apps/dock/test/hostile-app.test.ts`, the real hub and the real Pulse sandbox on Node's SQLite with simulated hostile apps, fetch routed by origin and counted; `trust.test.ts` for the rules alone):

| Attack | Stopped by | Test |
|---|---|---|
| An app on another domain calls itself "Pulse" | the id and `name` come from the domain (`domainAppId`), the declared name is `declared_name`; tool labels say "Unverified app at <host>" | name spoofing |
| It takes a verified app's prefix, `page`, or a lookalike's | domain ids always hold `_`, verified ids never; another origin with the same domain id is refused (`app_id_taken`); no dotless, IP or localhost host | taking another app's prefix |
| Its pin's `next` points the agent at another app | the hub builds `next`/`next_args` with the pin's own app id | taking another app's prefix |
| An answer too large (tools list, result, view) | `readCapped` in `app-client.ts`, the declared length first; views over 8 KB not kept | oversized responses |
| An answer that never comes, or never ends | `deadline` races the fetch and every body read | slow responses |
| A blocked domain, before or after pairing | `appVerdict` at pair time; `pairings()` reads it as `blocked` on every call, so no "paired" query returns it; `givesBack` never calls it | a blocked domain |
| HTTP instead of HTTPS, or an MCP URL on another origin | `appVerdict` (`https_required`, `app_not_allowed`) | HTTP instead of HTTPS |
| A tool description, result, view or pin that tries to instruct the agent | the untrusted envelope and marks, the label, no annotations, a pin dated ahead ignored | … arrive marked untrusted |
| Pairing many apps into one dock | `LIMITS.pairings` | the pairing cap |
| An unknown app pairs without the person's informed yes | the warning's Approve (§ 18); the kill switch `UNVERIFIED_PAIRING=closed` | `open-pairing.test.ts`; the kill switch |
| Instructions in a JSON-RPC error message or an HTTP error body | `AppCallError.reason` / `failureReason`: an unverified app's failure is told in the hub's words only | error messages |
| `then` or `page_open` on every answer, to keep the agent waiting | `presence()` counts verified apps only | the wait loop |
| Blocked pairings filling the cap | the cap counts pairings read as pending or paired | blocked pairings hold no place |
| A blocklist entry in Unicode against a punycode host; a host too long for an id | `blockedHost`, `allowedOrigin`; `app_host_too_long` | a Unicode blocklist entry … |

**A note on sizes.** The byte cap on an answer counts bytes as read. The smaller caps on what the hub keeps of an unverified app (a view under 8 KB, a schema under 8 KB, `next_args` under 1 KB) measure the JSON's length in UTF-16 code units, not bytes, so non-ASCII text can make a kept view up to about three times that in UTF-8. Each is still bounded, by that cap and by the answer's byte cap, and marked untrusted.

Not covered: a rate limit on an app's pins; and what the agent does with marked text, which no hub can decide for it.

## 16. The Direct profile packaged, and `apc_link` (TIN-578)

Since this section, Pulse and Signals offer both profiles on their deploys; § 14's "Pulse runs Dock only, Signals offers Dock" describes the state before it.

**Profiles in one place.** Each app declares how agents reach it in `APC_PROFILES` (`"direct,dock"` in `apps/demo/wrangler.jsonc` and `apps/signals/wrangler.jsonc`; `parseProfiles` in `@tineira/apc-server`, both when missing). Every check that used to hide Direct behind `APC_V2` (making an agent, a restricted agent, giving a shared URL its own, the cleanup of grants with no dock link) reads it instead; `APC_V2` keeps only what is not about profiles (the dataset route, Start over, the signup codes). An app that offers one profile refuses the other's routes.

**The Direct profile in the packages.** An app no longer builds Direct itself:

| Part | Where | What it does |
|---|---|---|
| A grant per agent | `newDirectGrant()` in `@tineira/apc-server` (`direct.ts`) | an id and 128 random bits of secret; the app keeps them in its own grants table |
| Its secret MCP URL | `directMcpUrl(origin, sid, secret)` | `{origin}/mcp/{sid}/{secret}`: whoever holds the URL holds the grant |
| What a connection says | `initializeOf(body)`, `linkClient(client, path)` | the client's name, title, icons; on the Dock path the agent's client as the hub names it |
| Names | `cleanAgentName` | plain text, one line, 40 characters |
| The agent list | `<apc-direct-agents>` in `@tineira/apc-web` (`direct-agents.ts`) | the person makes an agent (`apc-add`), names it (`apc-rename`), and copies its URL and the prompt to paste to it (`connectPrompt`) |
| Revoke | core (§ 14) | ⊘ in the agent bar |

Pulse's grants, its sandbox's Direct routes and its Agents screen use them (on the standard's deploy the screen is **Agents** again, with "Agents connected directly"). Signals takes Direct agents and `apc_link` with about 115 lines of server code of its own and 70 on its page, nothing of it a reimplementation of the packages: `addDirectGrant`, `renameGrant` and `unlinkGrant` in its feed, three routes, the client on `initialize`, the link offer around its tools, Revoke of both grants, a grants table whose `hub` and `agent` may be null (an older feed's table is made again on start), and a Connect panel on its page around `<apc-direct-agents>`. A visitor with no dock gets a feed on the same world as everyone (TIN-621). The dock's landing card "Connect app by app" opens Signals with that panel (`?connect`), beside "Open your dock", with equal weight.

**The agent bar's rule** (`<apc-agents>`). Each agent shows the path it came by: *direct*, *via dock*, or *direct + dock* when linked, with **unlink**. With any agent that came directly the bar is always shown in full: the app is the only place the person sees and points that agent. When every agent came through a dock, the person may collapse the bar (‹) to a small indicator of who is reading (their icons and "2 reading"); it is never hidden, and a click opens it again. The pins on the page (`<apc-pin>`) stay visible and draggable either way. While an agent that came only directly is connected, the bar shows a quiet hint, **Use this agent across apps with the dock** (apc.tineira.com), until the person dismisses or follows it, once per browser; an app turns it off with `dockHint = null`.

**`apc_link`** (APC 0.4, `packages/protocol/src/core.ts`). The same agent connected both ways would otherwise be two marks in the bar. When a connection arrives (`initialize`) with the same MCP client as one already connected on the opposite path to the same app, the app puts `apc_link: { code, expires_in: 120, note }` on a result of the new connection, like `attention`; the agent sends the code back with `apc_link({ code })` on its other connection (through the dock, `<app>__apc_link`), and the bar shows one agent with both paths. It is in the core's instructions and the `guide` prompt (`@tineira/apc-server`) and in the dock's instructions, so an agent knows the step is legitimate; an agent that ignores it stays two entries.

- `ApcLinks` in `@tineira/apc-server` (`links.ts`) holds the state in a small synchronous key-value store (`sqlKv` on the Durable Object's SQLite, or `memoryKv`): the links, each grant's current MCP session (its client, and whether an offer is still due), and the codes by SHA-256. Every check and write happens after its one await, with nothing in between.
- An offer is due when the connection arrives and someone with its client is connected on the other path, neither linked. It rides on the next successful result, at most once per session; on the Dock path only on one of the app's own tools, since the hub merges core results (`get_current_view`, `wait_for_focus`) into its own and would drop it. A new `initialize` is a new session.
- The hub initializes an app as itself (`clientInfo.name` "apc-hub"), so it now names the agent's own client in `params._meta["apc.tineira.com/agent_client"]` of that `initialize` (`initializeApp` in `apps/dock/src/worker/app-client.ts`, one argument from `introduce` in `hub.ts`). It names it to verified apps only (§ 15): an unverified app learns nothing of the agent's client, so it is never offered a link through the hub, and its results come wrapped as untrusted anyway. The hub needed no other change: it relays a verified app's results with every key but `attention` and `then`, and lists `apc_link` among the app's tools.
- Linking grants nothing: each grant keeps its own access, trimming and pin. A linked agent shows once in the bar, under its Direct grant (dragging its mark pins that grant; the dock still points the other). Revoke on it revokes both grants (both URLs answer 403 `revoked`); unlink removes only the link.

Every way a code could be abused, and what closes it:

| Abuse | Closed by |
|---|---|
| Guessing a code | 96 random bits, 120 s, the app's rate limits, and only the connections it was offered to can redeem it |
| Using it twice | marked used on success; a second redeem is `used` |
| Using it late | `expired` after `expires_in` |
| Sending it back on the connection that got it, or on another of the same path (two Direct grants merging) | `same_connection`, `same_path` |
| Another agent on the other path (another client, or one that connected after the offer) | the code is bound to the connections offered it: `not_offered` |
| A sibling of the same client (another window of the same agent product, on the opposite path) redeeming the code | **not closed, by design** (TIN-607): "the same client" is the MCP client's name, not a process, and the app cannot tell two windows of one product apart. Any sibling that was a candidate when the code was offered may redeem it, so the entry can group the wrong sibling. It needs the code, which only the offered connection receives; nothing is granted, and the person can unlink |
| Linking an agent that is already linked, to steal its entry | `already_linked` |
| A code from another app or another person's sandbox | codes live in one app's sandbox: `unknown_code` |
| Getting access through a link | linking grants nothing: no grant, trim or pin changes |
| Keeping a revoked agent through its link | Revoke cuts both; a revoked grant's link and codes go |
| Being asked again and again | once per MCP session |
| Reading a code from storage or the log | only its hash is kept; Pulse's event log writes `(hidden)` for it |
| A page, an app result or a reading that writes "apc_link" to trick the agent | the note says to answer only the app's own `apc_link` key; the worst case is a wrong grouping the person can unlink, with nothing granted |

**Tests.** The conformance suite has the `apc_link` checks (an adapter's `link`): one offer per session and the code links; refused on the same connection, the same path, another client, an unknown code and once used; refused when expired, with no new offer in that session; no offer between two clients; Revoke on a linked agent cuts both grants; unlink makes two agents again, each with its own grant. Pulse and Signals pass the suite on both profiles (`apps/demo/test/conformance.test.ts`, `apps/signals/test/conformance.test.ts`). `apps/dock/test/apc-link.test.ts` runs the real hub and the real Pulse sandbox: the same agent links both ways round (the code relayed by the hub and answered directly, and the other way), Revoke cuts both, and unlink keeps both working. `packages/server/test/links.test.ts` covers `ApcLinks` alone.

## 17. Discovery with `apc.json`, and an answer to a drop an app cannot take (TIN-579)

**The file.** Every APC origin says what it is at `GET {origin}/.well-known/apc.json` (APC 0.5, `packages/protocol/src/manifest.ts`), served by that origin, public, as JSON of at most 16 KiB:

```json
{ "name": "Signals", "standard": "0.5.0", "origin": "https://signals.apc.tineira.com",
  "profiles": ["direct", "dock"], "mcp": { "path": "/mcp/" },
  "direct": { "connect": "https://signals.apc.tineira.com/?connect" } }
```

| Key | What it says | Why it is there |
|---|---|---|
| `name` | what the app calls itself | for people and tools; the hub still names an unverified app by its domain (§ 15) |
| `standard` | the version of the standard it implements | the conformance suite and a reader know which contract to expect |
| `origin` | exactly the origin it is served from | a file that names another origin is refused: an app cannot borrow another's |
| `profiles` | `direct`, `dock` or both; `hub` alone for a dock | what the app supports, and a dock told apart from an app |
| `mcp.path` | every grant's MCP URL on the origin starts with `origin + path` | the domain's own `/.well-known/` vouches for where its grants live (below) |
| `direct.connect` | with `direct`: the page on its own origin where the person connects an agent | what a person is shown when a dock agent's drop cannot be taken |
| `dock.pair`, `dock.confirm` | a hub's pairing endpoints, on its origin | a tool finds where a dock pairs |

It is the smallest shape that does two jobs: a dock learns what an app supports, and confirms that the app controls its domain. Whoever controls the origin's root controls `/.well-known/`, so `origin` and `mcp.path` there are the domain's word, not the word of whoever sent `POST /apc/pair`: on a shared host where tenants serve paths of one origin, a tenant's MCP URL outside the declared path never pairs. A reader ignores profile words and keys it does not know, so later versions can add them. `@tineira/apc-server` builds an app's file from what the app already declares (`apcManifest({ name, origin, profiles: parseProfiles(env.APC_PROFILES), connect })`, `apcJsonResponse`); Pulse (`/agents`), Signals (`/?connect`) and the dock serve theirs from their Workers, before the `/.well-known/*` 404 that tells an MCP client there is no OAuth. The answer may be cached for five minutes and read from any origin.

**The dock reads it at pairing.** `pair()` in `apps/dock/src/worker/hub.ts` reads the app's file once the ticket, the app's origin (`appVerdict`) and the room for a pairing (the cap, a domain id) have passed, so nobody can make the hub fetch an address it would not pair. The read follows § 15's transport rules (`readApcJson` in `app-client.ts`), stricter on one point: 5 s for headers and body, 16 KiB, and no redirect followed for any app, verified or not. The file is the origin's own or none: following a redirect would keep the target's body as the origin's file. A redirect is the origin answering, so it refuses the pairing for every app, verified too. It is never the "out of reach" that lets a verified app pair on its last copy. Then:

| The file | Error |
|---|---|
| answered with a 4xx | `apc_json_missing` |
| answered with a redirect (a 3xx, or the status 0 some runtimes give for one), any app | `apc_json_redirected` |
| not JSON, over 16 KiB, a field missing or malformed, a `direct.connect` off its origin | `apc_json_invalid` |
| names another origin | `apc_json_wrong_origin` |
| lists no `dock` (a Direct-only app, or a hub) | `dock_not_offered` |
| the MCP URL the app sent is not under `origin + mcp.path`, or carries an encoded `/`, `\`, `.` or `%` after it | `mcp_url_not_declared` |
| no answer, a time limit or a 5xx, from an unverified app | `apc_json_unreachable` |

**Under `mcp.path`, and only there.** `declaresMcpUrl` checks the URL as parsed (http or https on the app's origin, no credentials, the path under `mcp.path`) and the rest of its path as sent. The URL parser removes literal `.` and `..` segments, and some encoded ones, but a server may decode others after the hub has checked the path (`/mcp/%2e%2e%2fadmin`, `/mcp/..%2f..%2fadmin`, `/mcp/%252e%252e%252f…`, `/mcp/abc%2f..%2fdef`). So no `%2f`, `%5c`, `%2e` or `%25` may appear in the path as sent, and no `.` or `..` segment after `mcp.path`. Every URL in a manifest (`direct.connect`, a hub's `dock.pair` and `dock.confirm`) must be http or https as well as on the origin (`urlOnOrigin`): `blob:https://app.example/…` has that origin, and is no page of it.

**The copy it keeps, and a verified app's file out of reach.** The hub keeps each origin's last good copy in its own table (`apc_json`), for as long as the dock lives. For 10 minutes (`LIMITS.apcJsonFreshMs`) it uses the copy without asking; after that it reads the file again. A definite answer (no file, a redirect, an invalid file, another origin) refuses the pairing and forgets the copy, for a verified app too: a verified app that stops offering Dock stops pairing. Only when a verified app's file cannot be reached at all (no answer, a time limit, a 5xx) does the app keep pairing: checked against the last copy the hub read, or, with no copy, on the operator's word, since the app is in `APP_ORIGINS`. The operator's word covers the profile check only. The path guard still holds without a file: the MCP URL must lie under the default path, `APC_DEFAULT_MCP_PATH` (`/mcp/`, `@tineira/apc-server`'s default `mcp.path` and the path Pulse and Signals use), with the same checks for encoded traversal. So no MCP URL pairs outside a declared or default path. A verified app that serves its grants elsewhere pairs only while its file can be read. Its MCP endpoint is called within seconds anyway, so a pairing with an app that is really down fails there. An unverified app has no operator's word: unreachable refuses it. The hub reads the file only when an app asks to pair; a pairing made stays until it is revoked, unpaired or blocked, whatever the file says later. CI deploys Pulse and Signals before the dock, so a dock that asks for the file never meets an app that does not serve it yet.

**A refused pairing uses up the drag's ticket.** The hub deletes a ticket as it reads it, before it reads the app's file, so a ticket is single use whatever happens next. When the file refuses the pairing, the app shows the error and the person drags the agent again for a new ticket. A refusal for the app's file is not something the person can fix by retrying, so the drag is not worth keeping; the cost is a second drag after a transient failure.

**A drop an app cannot take.** A dock agent dropped on an app that offers only Direct would otherwise be lost: the app would ignore it, or (without native drops) the browser would refuse it, and the person would see nothing happen. Now it is answered:

- **In the page** (`@tineira/apc-web`, `packages/web/src/pinning.ts`). `enablePinning` takes `profiles` and `direct: { name, connect }`. `profiles` is what the app's `apc.json` says: a list, a promise of one, or a loader such as `loadApcProfiles`, which reads the page's own file the way the hub and the extension read one (no cookies, no redirect followed, 3 s for headers and body, 16 KiB). Pulse and Signals pass `() => loadApcProfiles()`, so the page knows its profiles from the same file the dock reads, before its own state has loaded. While the profiles load, a dock agent's drop is taken anywhere on the page and held for 3 s at most; once the profiles are known it is answered or sent to pairing as they say (the ticket lives 60 s). When they cannot be read, the drop is not sent to pairing, because the page cannot tell whether its app takes dock agents. It is answered as `unchecked`, with `couldNotCheckNote(name)`: "*Signals* could not check how it connects agents just now, so your agent was not paired. Drop it again in a moment, or connect your agent to *Signals* directly on its own URL." The loader is asked again on the next dock drop. Sending it to `onUnknownAgent` instead would not be unsafe, since the hub reads the same file before it pairs, but it would put the person through consent in the app for a pairing that may never be allowed. Without `dock`, it takes a dock agent's drop anywhere on the page, lights no target, never calls `onUnknownAgent` or `onPin` for it, and calls `onDockUnsupported({ drag, target, name, connect, reason, message })` (`reason` is `direct_only` or `unchecked`), or by default shows a note at the bottom of the page with the message and a link to the connect page (`showDockUnsupported`; a new drop replaces the note, never a stack; the link only when `connect` is an http(s) page of the app's own origin). The words are `directOnlyNote(name)` in `@tineira/apc-protocol`: "*Signals* connects agents directly, not through a dock. Connect your agent to *Signals* on its own URL, then drag its mark from the agent bar there." Signals opens its Connect panel with them; Pulse opens its Agents screen. While it takes native drops, `enablePinning` sets `data-apc-native-drops` on the page's root element.
- **In the browser extension** (`apps/extension/src/content.ts`, `directOnlyGate` in `drop.ts`). On an APC app (§ 13.2) it still reads and pins nothing, except on one that would lose the drop; a drop the app leaves unanswered gets this card too, with the extension's words for it (§ 13.2). The first drag of an agent over an APC app asks the service worker for the app's `apc.json` (read from the page's own origin, without cookies or redirects, 3 s and 16 KiB at most; `lookUpDirectOnly`). The service worker keeps a file it read and understood, Direct-only or not, for 5 minutes, and a lookup that told nothing (no file, an error, no answer) for 30 s only, so a page that was briefly unreachable is asked again soon. The page keeps a real answer, and asks again after a lookup that told nothing, on a later drag once those 30 s have passed. A page with `data-apc-native-drops` answers its own drops and is never taken from. On any other APC app, the extension takes the drop while the app may be Direct-only: once its file says so, and while the lookup is still on its way, so a quick first drop is never lost. The drop is caught in the capture phase, before the page's own handlers, and held from them (`stopImmediatePropagation`), so a page with an older `@tineira/apc-web` never acts on it and then gets a card too. On an app known to be Direct-only, the card comes at once. A drop held while the lookup is in flight gets the card when the file says Direct-only. Otherwise it goes back to the page: the same drop, dispatched again on the element it landed on with the same data, untrusted, so the extension lets it through. The card, where the agent was dropped, replaces any card before it. Its words are the extension's, so they lend the page's chosen name no authority: the domain first, as the dock names an app it does not know, then "This page says it is "*Signals*" (*signals.example*). It connects agents directly, not through a dock: connect your agent to it on its own URL, then drag its mark from the agent bar there.", and the link "Connect an agent on *signals.example*". Nothing is sent anywhere. The link is the app's `direct.connect`, which the parser accepts only on the app's own origin, so a page cannot use the card to send the person elsewhere.
- **Pulse's profiles have one source.** `servedProfiles(env)` in `apps/demo/src/worker/sandbox.ts` (what `APC_PROFILES` declares, with Dock only on the standard's deploy, `APC_V2`) is what its `apc.json`, its page (`state.profiles`) and its own checks use, so the page never tells the person something its file contradicts.

**Conformance.** The suite's first check reads the app's `apc.json` through the adapter's `fetch` (Pulse's and Signals' adapters route it to their Workers): HTTP 200 as JSON, at most 16 KiB, valid for the app's origin, a `standard` from 0.5.0 up to the suite's own version, never `hub`, the profile under test listed (both when the adapter has `link`), the grant's MCP URL under `mcp.path`, and `direct.connect` on the origin. Pulse (both profiles, and its direct-only setup) and Signals (both profiles) pass; `apps/demo/test/conformance.test.ts` checks that the suite fails a file that leaves out a profile the app serves, names another origin or MCP path, claims a newer standard, or is missing.

**Tests.** `apps/dock/test/apc-json.test.ts` runs the real hub with the real Pulse sandbox and Pulse's Worker: Pulse, Signals and the dock serve valid files; a ticket that does not pass reads nothing; ## 18. Open pairing, with a warning in the dock (TIN-581)

**The person decides, not a flag.** Any APC app can ask a dock to pair: one on HTTPS, on a domain name, that offers the Dock profile in its own `apc.json` (§ 17), and passes every rule of § 15. An app outside `APP_ORIGINS` asks the way Pulse does (`POST /apc/pair` with the drag's ticket, after consent in its own page), and its request waits in the dock as a pending pairing. It becomes a pairing only when the person approves the dock's warning for its domain. Verified apps keep the flow of § 12: their request carries no warning and the usual Allow pairs them.

**The warning** is the dock's, never the app's page, which could draw anything. It shows wherever the dock shows a request (the dock, an agent's page, Float, the strip and the pets: `UnverifiedRequest` in `apps/dock/src/web/unverified.tsx`), with its words from one place (`unverifiedWarning` in `apps/dock/src/worker/trust.ts`), in this order:

- the domain, first and big: the only name the dock gives the app (§ 15);
- **Not verified**;
- what the app calls itself, only as secondary text and marked as its own word: "It calls itself "Pulse Pro": that is what the app says about itself, and the dock has not checked it.";
- who would read it, and the risk: "Your agent will read whatever this app tells it, and that could lead your agent to move data out of your other apps.";
- **Deny**, first, styled as the main button and focused, so Enter denies; then **Approve**.

**Once per domain per dock.** Approve sends `approve_unverified`, and the hub records the app's origin in the dock's `unverified_ok` table. A later request from that origin, for another agent in the dock while the approval stands, carries `warning: false` and is the usual request with the **Not verified** badge and Deny / Allow (`approve`). Deny, Unpair or Remove on an unverified app, in any state (pending, approving, paired, or held by the blocklist or the kill switch), removes the origin's record, and so does removing an agent for its unverified apps: the next request from that domain warns again. A denial is never remembered against the app. Verified apps have no record, and their Unpair is unchanged. The hub, not the page, enforces it: while the origin has no record, `approve` on its request is refused as `warning_required`, so a dock page cached from before (the dock is an installable app with a service worker) cannot pair one without the warning. `approve_unverified` on a verified app's request is `invalid_action`.

**Approving, then paired.** A yes does not pair at once. The hub then introduces itself to the app (`initialize`, `tools/list`), which awaits the app, and a Durable Object takes other requests during an await: a Deny from another click or surface can arrive meanwhile. So the row goes `pending` → `approving` → `paired`. While `approving` nothing is relayed to the app (every relay reads `paired` rows), the dock shows the request with Approve off and Deny on (`approving: true`; `/apc/confirm` answers `pending`), a second Approve is `invalid_action`, and a Deny wins: it deletes the row, clears the origin's record and gives the grant back. `introduce()` reads the row again after every await and stops when it is gone or blocked, so the app gets no call after the Deny, and `decide` answers `unknown_pairing` instead of pairing.

**Settling an approval** (`settleNow`). When the introduction ends, the row turns `paired` only if, at that moment, nothing holds it (not on our blocklist, not an unverified app while the kill switch is closed) and, for an unverified app, its domain's approval still stands. Otherwise it is never stored as paired: the row goes, with the domain's approval, so the person approves again later, and `decide` answers `app_blocked` (held) or `approval_withdrawn` (approval gone). The app gets its grant back only if it may be called, so never while held. An approval whose introduction never finished (the object evicted mid-way, or the introduction stalled past the minute) is settled the same way after `LIMITS.approvingMs`, a minute. Should the Approve's own `decide` resume after that settled it, it finds the row stored `paired` and answers `{ ok: true }` (or `app_blocked` when a hold came since), keeping the domain's approval, instead of `approval_withdrawn` for an app that is in fact paired (TIN-609): `decide` sets the alarm for `approved_at + approvingMs` as it starts approving, and `arm()` always includes the oldest such row, so the alarm settles it on time; a paired one has its tools read on first use, as after a failed introduction. Under vite dev alarms are not set, and the same work runs on the next `state`, `pair` or `decide`, which the dock page asks for on every change it hears of. On every surface (the dock, an agent's page, Float, the strip, the pets), and on the one that sent the Approve too, an Approve on its way, or the hub still approving, turns only Approve off: Deny stays on, so a misclick can be undone, and the Deny reaches the hub, which lets it win (above). A Deny on its way turns both off. The page tracks the two kinds of answer apart (`request-state.ts`: `buttonsOff`, `mayAnswer`), and a card tracks only an Approve it sent itself until the page re-renders: a Deny is the page's alone, so one that fails is cleared there and can be sent again (`landed`, `cardInFlight`).

**Every change before any await** (Fix check 4 on #120). A Durable Object takes other requests while one awaits, so the hub makes every change of a removal in one synchronous block and only then awaits the apps: Deny and Unpair (`decide`), removing an agent (its pairings, pointers, readers, calls, the agent, and its unverified domains' approvals), pending expiry (which, as a deny would, also takes an unverified request's domain approval) and settling an approval all delete first and give grants back afterwards, from a snapshot. A `decide` on a pairing that is already gone then fails (`unknown_pairing`) before it inserts anything. An Approve re-reads its row after every await (`arm`, `introduce`), and records whether it inserted the domain's approval (a nonce on its `unverified_ok` row): when it ends without a settled pairing (`unknown_pairing`, `revoked`, `app_blocked`, `approval_withdrawn`), it removes the approval it inserted, and only that one, so an approval that stood before the call stays. An introduction that fails without removing the row (no answer) still settles as before: paired, with the error shown and tools read on first use.

**One approval per domain, for the whole dock.** Because the approval is the dock's, not the agent's, a Deny, Unpair or Remove of a domain anywhere in the dock (removing an agent included) also withdraws another agent's Approve of that domain still in flight: when its introduction ends the approval is gone, so the pairing is dropped and `decide` answers `approval_withdrawn`. This fails safe, since the person sees the warning again on the next request. The dock never drops a refused answer silently: a 400 `{ ok: false, error }` from `decide`, or a call that fails, is shown where the answer was given (the dock, the agent's page, Float, the strip, the pets) as a notice (`decisionNotice` in `request-state.ts`, `DecisionNotice` in `unverified.tsx`): "Approval was withdrawn; ask again." for this case, and plain words for the others.

**Never framed.** The owner's cookie is `SameSite=Lax`, so a page on a same-site host (`pulse.apc.tineira.com`) would get it in an iframe of the dock, and could lay its own content over the warning's Approve. Every response from the dock's Worker carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` (a middleware in `apps/dock/src/worker/index.ts`, assets it hands out included, a WebSocket upgrade excepted), and `apps/dock/public/_headers` sets both for the assets served without the Worker (`/dock`). Float is a Picture-in-Picture window and the desktop dock a top-level webview, so nothing of ours frames it.

**A host on one line.** A narrow surface (the pets' 240 px bubble, Float) wrapping `pulse.apc.tineira.com.evil.example` would put `pulse.apc.tineira.com` alone on the first line. The dock shows every unverified host with `HostName` (`unverified.tsx`): on one line, the registered domain (`splitHost` in `trust.ts`: the last two labels, three under a country's second level such as `co.uk`, with the port) always whole, the labels before it shortened from the left ("…tineira.com.evil.example"), the full host in its title. Only a registered domain wider than the card wraps, inside itself.

**Where it shows after.** An unverified app carries the **Not verified** badge in the agent's apps, on the tile and the agent's page where the agent points, and on a blocked line. To the agent nothing new: its tools, views, focus and results come as § 15 marks them (labelled with its host, no annotations, the untrusted envelope), and the hub's instructions say that an app the dock has not verified is named by its domain and comes marked untrusted.

**Requests expire.** A pending pairing nobody decides goes after `LIMITS.pendingMs`, 10 minutes, as a deny would: the row goes, the app gets its grant back (`/apc/revoke`), and its place under the cap of 20 frees. This holds for every app, verified ones too: an undecided request held a place under the cap forever. The hub's one alarm (§ 13.5) rings for the oldest pending request too, and `pair`, `decide` and the dock's state expire stale requests first, so an answer that comes late finds `unknown_pairing`. Those three make the changes at once and give the grants back after they answered (TIN-609: `later`, with `ctx.waitUntil`), so the dock's state and an app's `/apc/pair` never wait on another app's `/apc/revoke` (up to 10 s); the alarm awaits its give-backs. Pulse already handles a link the hub forgot: on the next drop `/apc/confirm` answers `not_paired` and Pulse asks the person again.

**Dock pages left open** (TIN-609). The hub enforces the warning, but a dock page loaded before it (one that sends a plain `approve` for every request and ignores a 400) only sees its Allow do nothing. The dock's service worker caches nothing, so such a page is simply one left open since an earlier deploy. `apps/dock/public/sw.js` now carries a `VERSION`, changed when open pages must not keep their code: the browser installs a changed worker on its next update check (any navigation in its scope, and every page of the dock's asks on becoming visible), and the new worker takes over at once (`skipWaiting`, `clients.claim`). The worker never navigates or waits on a client: a navigation's fetch waits for the worker to finish activating, so a worker that awaited one in `activate` would hold every fetch of the origin, V1's included (Grok's fix check on #123). The page reloads itself instead (`keepDockCurrent`, `apps/dock/src/web/sw-reload.ts`): a dock page (`/dock`, `/dock/…`) that had a worker when it loaded hears `controllerchange` and reloads once, never twice within 30 s (sessionStorage). The landing, `/extension` and V1 at `/v1` (another Worker on this host, inside the worker's scope `/`) never reload, the worker never answers a V1 navigation, and a first install reloads nothing. A page loaded before this deploy has no such listener: it keeps its code until the person reloads it, and the hub still refuses its plain approve (`warning_required`). A reload closes Float, as any reload of the dock does. On a current page `warning_required` says that the request now shows its warning, and the request re-renders with it.

**The kill switch.** `UNVERIFIED_PAIRING` (`apps/dock/wrangler.jsonc`, `"open"`; unset is open too) set to `closed` and deployed closes the dock to unverified apps in an emergency: `/apc/pair` refuses them (`app_not_allowed`), a request waiting cannot be approved (`app_blocked`), and every unverified pairing reads as `blocked` with `blocked_by: "closed"`, so the hub never calls it and keeps nothing of it (§ 15's blocked state), and the dock shows it as **Paused**. Set back to `open`, they are paired again, their tools fetched anew. Verified apps are untouched. Our blocklist (`BLOCKED_APPS`) wins over an approval as before: a blocked domain cannot pair or be approved, approved before or not.

## 19. On mobile, every app shows the agent in its page (TIN-608)

**The decision.** Whatever an implementer chooses for its profiles or its agent bar, on mobile every APC app shows the agent in its own page. On a phone there is no dock window, browser extension or desktop pet to drag an agent from, so the agent in the page is the only way the person can point it (give it focus). It is in the core (`core.ts`, item 9, and `packages/protocol/README.md`), so it holds on both profiles, and APC 0.6.0 carries it.

**What is a mobile viewport.** `APC_MOBILE_MEDIA`, `(pointer: coarse), (max-width: 640px)`: a device whose primary pointer is a finger (phones, tablets), or any window narrower than 641 px. Both, because either one alone misses a case: a narrow desktop window has a mouse but no room for a bar beside the page, and a tablet in landscape is wide but has no mouse. The reference viewport for checks is `APC_MOBILE_VIEWPORT`, 375 x 812.

**The bar.** `<apc-agents>` (`packages/web/src/agents-bar.ts`):

- Never collapses on mobile: `barCanCollapse(agents, mobile)` is false there, so the Dock profile's collapse rule (§ 16: a bar of dock agents only may fold to who is reading) does not apply. An app cannot make it collapse by passing `paths`.
- Is fixed at the bottom of the viewport: reachable while the page scrolls, in the thumb's reach, whatever the app's header does. It reserves its height at the bottom of the page, as `--apc-bar-height` on `<html>` and `padding-bottom` on `<body>`, so it covers no content, and everything else the app fixes at the bottom can sit above it with `calc(... + var(--apc-bar-height, 0px))` (Pulse's tour panel and `showDockUnsupported` do). When the viewport stops matching, it goes back to where the app put it. Two bars in a page (Signals has one in its side column and one in its mobile header) are fine: only a visible one takes room.
- Has finger-sized parts: the mark is 44 px, and the pin dot, the pin's ×, Unlink, Revoke and the warning have a hit area of about 40 px or more (a transparent extension where the shape is smaller). The pin badge's × (`<apc-pin>`) too. The dock hint ("Use this agent across apps with the dock") is not shown on mobile: there is no dock window to move to.
- Wraps and scrolls inside `40vh` when many agents make it tall.

**Pinning with a finger.** Browsers on phones do not do HTML5 drag and drop, so the dock's drop (`application/x-apc-agent`) never happens there; the agent in the page pins with pointer events, which iOS Safari and Android Chrome do deliver. `enablePinning` (`packages/web/src/pinning.ts`) takes both ways, with no option to set:

- **Tap to pin** (the default, and the one that works reliably: no gesture to learn, no conflict with the page's scrolling). The person taps the agent's mark: the agent is armed (`aria-pressed` on the mark, a 3 px outline), every target on the page is outlined (`body.apc-armed`, `apc-dragging`), and a note above the bar says "Tap what to point *Claude* at." with Cancel (44 px). The next tap on a target pins the agent there, innermost `data-focus` first, as a drag does, and the page's own action for that tap does not run (the click that follows is swallowed). A tap on something that is not a target lets go and passes through (see After review); a target the agent may not point at (`canTarget`) says so and keeps it armed. Tapping the mark again, Cancel, Escape or a pin lets go. A scroll is never a tap: the browser cancels the pointer, and a press that moves 10 px or more is not one (`TAP_SLOP_PX`). Armed state is `createTapPin`, pure and tested; a keyboard activation of a mark arms it too, with a keyboard way to pin (see After review).
- **Touch drag.** Pressing the mark and dragging it with a finger works as the mouse drag does (the mark has `touch-action: none`); a press that does not move is a tap, as above. `pointercancel` ends a drag, which before left the ghost mark in the page.
- A mouse click on a mark does nothing, as before. A pin badge (`<apc-pin>`) can be dragged by touch but a tap does not arm it: it is where an agent points, not where agents are. Unpin is the × beside the agent's pin dot in the bar (or on its badge): a tap.

**Pulse and Signals** use all of it through `<apc-agents>` and `enablePinning`, which they already used: no change in either app's components. (Pulse's tour panel got the `--apc-bar-height` offset.) They show their agents on mobile whatever their profiles: the bar is there for a Direct agent, a Dock agent or both.

**Conformance.** An adapter may give `page.mobile` (`ApcMobilePage`: `agentBar()`, `pinByTouch(grantId, target)`, `unpinByTouch(grantId)`). Then the suite checks, at 375 x 812: every connected agent is shown in the page and the bar cannot be collapsed or hidden; a pin made by tapping the agent and then the target, with no mouse drag, is read by the agent through `get_current_view` (twice, the second replacing the first), and unpin by touch removes it. Pulse's and Signals' node tests model the page with `@tineira/apc-web`'s own pieces (`barCanCollapse` on mobile, `createTapPin`) on both profiles, and a test checks that the suite fails a page that collapses its bar, hides an agent or cannot pin or unpin by touch.

**Verified in a real browser.** `scripts/mobile-e2e.mjs` drives Chrome at 375 x 812 with touch emulation and real touches (DevTools Protocol `Input.dispatchTouchEvent`, so the page gets trusted `pointerType: "touch"` events) against Pulse and Signals running locally, and runs the same mobile checks with an adapter that taps in that page: the bar's marks are in view, at least 40 px and not covered; a tap on the mark arms it; a tap on a target pins it; the agent reads the pin through its MCP URL; the × removes it. It also checks Cancel, tapping the armed mark again, a tap on nothing, a finger drag onto a target, and a bar of dock agents only left collapsed by a desktop visit staying in full. Not covered: iOS Safari and Android Chrome themselves (only Chrome's touch emulation), and the Dock profile end to end on a phone (the hub's drop is a desktop gesture; a dock agent's grant is pinned from the same bar).

**After review (TIN-608).** Five changes to the above:

- **Only the person's own events point an agent.** `enablePinning` ignores any event with `isTrusted` false (a pointer press, move or release, a click that arms from the keyboard, Enter or Space that pins), and the bar's and badge's ×, Unlink and Revoke buttons ignore an untrusted click, so a script in the page (`element.click()`, a dispatched `PointerEvent`) cannot point an agent at data or unpin it. A test that sends its own events passes `trusted: () => true`; that is an option of the code calling `enablePinning`, not something a page can reach. The drop of a dock agent (`dragover` and `drop` with `application/x-apc-agent`) is a separate path with its own consent and is not changed here.
- **Armed never traps the person.** Only the click that follows the tap that pins (or is refused) is swallowed, for 500 ms from that tap. A tap on anything else lets go and passes through, so a link, tab or button works at once; Escape, `popstate`, `hashchange`, `pagehide`, a hidden page and any change of the URL (a `pushState` too, watched every 250 ms while armed) let go.
- **The keyboard pins.** Enter or Space on a mark arms the agent, makes every target focusable (`tabindex="0"`, put back on let go), moves focus to the first and says in the note how to pin; Enter or Space on a focused target pins there, Escape cancels.
- **Conformance requires the mobile adapter from 0.6.0.** An adapter without `page.mobile` fails the check "the page adapter for a phone is given" when the app's `apc.json` claims a standard of 0.6.0 or later. The node tests of Pulse and Signals still model the page: there is no DOM library in the repo's test setup (the fake DOM in `pin-badge.test.ts` is too small for a bar), so the real rendered bar is checked by `scripts/mobile-e2e.mjs`, which now runs in CI as the job `mobile-e2e` (Chrome on the runner, the two dev servers). It gates no deploy. It also checks that scripts cannot arm or pin, that a tap elsewhere passes through, that a route change lets go, and the keyboard path.
- **iOS safe area.** Pulse and Signals set `viewport-fit=cover`; the bar pads by `env(safe-area-inset-bottom)`, and the armed note and the Direct-only note offset by the larger of the bar's height and the safe area.
